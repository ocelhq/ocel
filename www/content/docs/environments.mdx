Every deploy lands in one of two deployed tiers, and `ocel dev` runs a third on your machine:

| Tier | What puts your app there | Values come from |
| --- | --- | --- |
| `production` | [`ocel deploy`](/docs/cli/deploy) | ocel's own store in your account |
| `preview` | [`ocel preview`](/docs/cli/preview), one per git branch | ocel's own store in your account |
| `dev` | [`ocel dev`](/docs/cli/dev) and `ocel run` | your project's `.env` |

Any tier can read its values from Infisical or a command instead; see [Env sources](/docs/env-sources).

## Production and previews are kept apart

A preview never reads production's values or touches production's resources:

- **Values.** Each deployed tier has its own store, and a value is sealed to the tier it was set
  for. A key set for production is not set for previews until you set it there too.
- **Infrastructure.** Each tier is bootstrapped on its own, with `ocel bootstrap production` and
  `ocel bootstrap preview`.
- **Resources.** Each preview provisions the database, bucket and other resources it declares,
  never sharing production's or another preview's, and `ocel preview rm` takes them with it.
- **Domains.** Production serves the hostnames under `domains.production`. Each preview gets a
  hostname under the `domains.preview` wildcard, ending in a random token.
- **Protection.** [`protection`](/docs/configuration#protection) switches the password per tier,
  and each tier holds a password and bypass secrets of its own: a preview password never opens
  production.

A hostname nobody can guess is not access control, so keep production secrets out of previews.

## Tiers and namespaces

A **tier** is a credential boundary: each tier is deployed with a credential of its own, whose
grants are held to that tier's resources as far as each cloud lets them be.

- **On AWS**, a deploy's grants on resources are held to its tier by a tier-named ARN or the
  `ocel:env-tier` tag of the resource, so each tier pushes to ECR repositories of its own and
  adopts only a certificate its own tier requested or one you brought. A few actions are
  account-wide: reads and lists such as ECR's login token, `ec2:DescribeRegions` and
  `acm:ListCertificates`, and `ecs:DeregisterTaskDefinition`.
- **On Google Cloud**, ocel binds the `ocel-tier` Resource Manager tag to every resource a deploy
  or bootstrap makes that can carry one. A deploy credential's roles on Cloud Run, Pub/Sub, Cloud
  Storage, Secret Manager, Artifact Registry, Firestore, Cloud SQL and service accounts hold on a
  resource carrying its own tier's value or no value. Within one project that is best effort: KMS
  keys are held apart by name, some roles are on the whole project, and some resources carry no
  tag. See
  [sharing one project between tiers](/docs/providers/gcp#sharing-one-project-between-tiers).

A **namespace** is lighter: every name ocel gives a resource starts with it, so two namespaces in
one account never collide, and tearing one down never touches another's. On Google Cloud the
`ocel-tier` tag key is the exception: every namespace in the project shares it, and tearing one
down keeps it. A namespace is `ocel` unless you set `OCEL_NAMESPACE`, and is meant for CI and
advanced setups that run several installations side by side. It is never a credential boundary.
`ocel permissions deploy` prints a credential per namespace. On Google Cloud the grants it holds by
tier tag reach every namespace of its tier; on AWS only those on resources whose ARN names no
namespace do, such as certificates and CloudFront distributions.

## Variables

Your app declares the variables it reads, and the declaration is where each one's class is set:

```ts title="resources/env.ts"
import { defineEnv } from "ocel/env";
import { z } from "zod";

export const env = defineEnv({
  NEXT_PUBLIC_SITE_NAME: { class: "plain" },
  STRIPE_SECRET_KEY: { class: "sensitive" },
  DATABASE_PASSWORD: { class: "secret" },
  LOG_LEVEL: { class: "plain", schema: z.enum(["info", "debug"]).default("info") },
});
```

Go, Python and Rust declare the same three classes; see [Env](/docs/sdk/env). Set each value
per tier:

```bash
ocel env set LOG_LEVEL=debug                               # production
ocel env set LOG_LEVEL=debug --preview                     # every preview
ocel env set LOG_LEVEL=debug --preview --environment pr-12 # one preview
```

A deploy that is missing a declared value stops and names the `ocel env set` that fills it.

### Classes

Every value is encrypted in ocel's store. The class decides where it may go from there:

|  | `plain` | `sensitive` | `secret` |
| --- | --- | --- | --- |
| Usable in browser code | Yes, as `NEXT_PUBLIC_*` or SvelteKit `public: true` | No | No |
| Read by your app | Once, at startup | Once, at startup | On every access |
| Picks up a changed value | On the next deploy | On the next deploy | Within about a minute |
| Can have a default | Yes | Yes | No |
| Quoted in a parse error | Yes | No | No |
| In build output | As is | As `[secret]` | As `[secret]` |
| Reaches an image build | No | Yes, as a build secret | Yes, as a build secret |
| `ocel env get --reveal` | Prints it | Prints it | Prints it after `--yes` |

### Which class to choose

- **`plain`** for anything that isn't confidential: feature flags, log levels, public URLs. It is
  the only class browser code can read.
- **`sensitive`** for a confidential value your app reads once, such as an API key. It never
  reaches a client bundle, an error message or the build output.
- **`secret`** for a value that rotates, such as a database password. Your app reads it on each
  use, so a rotation takes effect without a redeploy, and it has no default, because a missing
  secret should fail loudly. A page prerendered from a secret keeps the old value until the next
  deploy.

### Values your infrastructure publishes

A value your own infrastructure makes, such as an API key or a URL, can be published straight
into a tier's store by the program that makes it, with `bind.variables` from
[`@ocel/pulumi`](https://www.npmjs.com/package/@ocel/pulumi) or
[`@ocel/sst`](https://www.npmjs.com/package/@ocel/sst):

```ts title="infra/index.ts"
import * as random from "@pulumi/random";
import { bind } from "@ocel/pulumi";

const apiKey = new random.RandomPassword("api-key", { length: 32, special: false });

bind.variables({ API_KEY: apiKey.result });
```

The app declares `API_KEY` as it declares any variable, and reads it the same way. Each
`pulumi up` or `sst deploy` runs [`ocel env publish`](/docs/cli/env/publish) with every value
the call lists:

- A key is checked as `ocel env set` checks one: a key no app declares is refused, and so is one
  declared only in a folder, since a published value is set at the project root.
- A value given as a secret output, such as a Pulumi `secret` or an `sst.Secret`'s `value`, is
  published as a secret and must be declared `secret`; a `plain` or `sensitive` variable would
  carry it into the release. A variable declared `secret` must be published as a secret, since the
  program's state keeps any other value unencrypted. `ocel deploy` checks the pairing again, in
  case the declaration changed after the program last ran.
- The store records the program that published each value: `urn:pulumi:<stack>::<project>` for
  a Pulumi program, `urn:pulumi:<stage>::<app>` for an SST app. `ocel env ls` shows the
  publisher as its source, and `ocel env get` names it.
- Only the publisher changes its values: `ocel env set` and `ocel env rm` refuse them, naming the
  publisher, since its next run would write over a hand edit. Change the value in the program.
- Each run publishes the whole set again, so a key the call stops listing is removed. Removing
  the call removes only the values it wrote and no call has written since, so moving the call
  under a component, or out of one, keeps them.
- One call publishes for one tier, or one preview environment, and works before the project's
  first deploy. A second call in the program for the same tier or environment is refused.

### Variables in config

`{ "$env": "NAME" }` in [your config](/docs/configuration#bindings) is a variable too, set the
same way. It is how a password, connection string or key reaches a binding, and the app never
receives it.
