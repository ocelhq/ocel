An edge that caches your app's responses keeps a page until its lifetime ends. `cacheTag`
names the page, and `revalidateTag` and `revalidatePath` refresh it sooner. They work in any
Node framework: Express, Hono, Fastify, SvelteKit, and a plain handler. Next has its own
`revalidateTag` and `revalidatePath`, which work as they always do.

```ts title="app.ts"
import { cacheTag, revalidatePath, revalidateTag } from "ocel/cache";

app.get("/blog/:slug", async (req, res) => {
  cacheTag("posts", `post:${req.params.slug}`);
  res.send(await renderPost(req.params.slug));
});

app.post("/blog/:slug", async (req, res) => {
  await savePost(req.params.slug, req.body);
  revalidateTag(`post:${req.params.slug}`);
  revalidateTag("posts", { expire: 0 });
  revalidatePath("/");
  res.sendStatus(204);
});
```

`cacheTag(...tags)` tags the response the request is answering. Call it before the response
starts.

`revalidateTag(tag)` marks every response with that tag stale, so an edge serves it while a
fresh copy is made. `revalidateTag(tag, { expire: 0 })` purges them instead: the next request
waits for a fresh render. Use a purge for a page that must not be served again, such as one
published by mistake.

`revalidatePath(path)` does the same for the cached page at a pathname such as `/blog/a`, with
no query, and takes the same `{ expire: 0 }`. `/blog/café` and `/blog/caf%C3%A9` name the same
page.

All three do nothing where no edge caches the app, as in `ocel dev` and in tests. Call them
while handling a request, and call the two that revalidate before the response starts. Behind
an edge that caches the app, a call made outside a request throws, and a revalidation made
after the response began is lost to the Cloudflare gateway and logged, as is one that names a
tag no edge can store, such as a tag with a space. Never put a user or tenant id in a tag, because the tag names reach the edge in a
response header.

## Routes an edge may cache

A build states which routes may be cached in `ocel-route-table.json`, a route table that sits beside its
`hosting.json`, and `hosting.json` names it with `"routeTable": "ocel"`. Framework adapters
write it; a plain Node app that states none caches nothing by rule on any edge, though
CloudFront and the load balancer still keep a response that sets its own `s-maxage`. A build with a cached route declares the
`revalidation` need, which an edge serves by clearing what a revalidation names. Next keeps its
own route table and does not use this one.

```json title="ocel-route-table.json"
{
  "version": 1,
  "basePath": "",
  "trailingSlash": "never",
  "headers": [{ "src": "/(.*)", "headers": { "x-frame-options": "DENY" } }],
  "redirects": [{ "src": "/old/(.*)", "location": "/new/$1", "status": 308 }],
  "routes": [
    {
      "src": "/blog/([^/]+)",
      "function": "index",
      "cache": {
        "revalidate": 60,
        "expire": 600,
        "allowQuery": ["page"],
        "tags": ["posts"],
        "bypassToken": "0123456789abcdef0123456789abcdef"
      }
    },
    { "src": "/account", "function": "index" }
  ],
  "fallback": { "function": "index" }
}
```

- `src` is a pattern for the pathname after the base path, as the browser sends it: not decoded,
  and with no query. It must match the whole pathname, and is written in the subset of regular
  expressions that RE2 and JavaScript read the same way: groups `( )` and `(?: )`, classes,
  `|`, the quantifiers, `\d \w \b` and their negations, and escaped punctuation. Lookaround,
  backreferences, named groups, flags and `\s` are refused when the build is deployed, as is a
  group repeated with `*`, `+` or a count above one that holds a quantifier or `|`, such as
  `(a+)+`, which can take a matcher exponential time. An optional group, such as
  `(?:/([^/]+))?`, may hold either.
- `routes` are tried in order, and the first match wins. A path no route names goes to
  `fallback`.
- `headers` rules all apply, in order, over the headers your handler set. On a route with a
  cache rule, a rule's `Cache-Control`, `CDN-Cache-Control` and `Surrogate-Control` are left
  out: the cache rule sets the lifetime there.
- `redirects` are tried in order, and the first match is answered without reaching your
  handler. `location` is a path that begins with one slash, or an `http` or `https` URL, and may
  read the groups of `src` as `$1`. A path stays on your site: slashes a group puts at its start
  collapse into one. The request's query carries over unless the location has its own.
- `trailingSlash` is `never`, `always` or `ignore`. A `GET` or `HEAD` for the other form is
  redirected with a `308`, and a path whose last segment has a dot is left alone.
- A cache rule's `revalidate` is the whole seconds a response stays fresh, at least 1, and
  `expire`, if set, the seconds after which a stale one is no longer served, more than
  `revalidate`.
- `allowQuery` lists the query parameters in the cache key. Left off, every parameter is in it;
  an empty list puts none in. A parameter outside the list is not passed on when the edge fills
  the entry.
- `tags` are stamped on every response of the route, beside the ones `cacheTag` adds.
- `bypassToken` is described below. A table has at most one, shared by all its routes.

A table that is not valid, that sends a request to a function other than the build's root
function, or that caches a route without declaring `revalidation` refuses the deploy.

## Which responses an edge caches

An edge caches a response when it asks to and the response allows it. A response is cacheable
when it is a `GET` or `HEAD` answered with `200`, sets no cookie, and is not `private`,
`no-store` or `no-cache`. On a route with a cache rule, the rule alone sets the shared
lifetime: the `s-maxage` and `stale-while-revalidate` your handler sets are replaced by the
rule's, and its `CDN-Cache-Control` and `Surrogate-Control` are dropped. Its `max-age` still
reaches the browser. On a route with no rule, the lifetime comes from the response's own
headers.

A cache rule governs only its own route. Only a route with a rule gets the rule's lifetime and
has its request's cookies stripped. A route with no rule, and a path that falls through to
`fallback`, keeps the cache headers your handler and your header rules set, as plain HTTP
does, and an edge stores the response whoever asked for it: CloudFront for as long as its
`Cache-Control` or `Expires` allows, and the load balancer for as long as its
`CDN-Cache-Control` allows or, without one, its `Cache-Control` or `Expires`. Both take a
`max-age` as the shared lifetime when there is no `s-maxage`, so mark a personalised response
`private` on such a route. On Cloudflare a route with no rule is not stored, whatever its
headers say.

Behind an edge that caches, a cached route answers everyone the same, so your handler never
sees a `Cookie` header on a `GET` or `HEAD` for it, and the response is safe to store on every
edge. A request with an `Authorization` header takes no lifetime from a rule, and a response
to it that keeps a browser lifetime is made `private`, so no edge stores it. A response that
sets a cookie is never stored.

### Previews and draft content

A request carrying the route's `bypassToken` in the `__prerender_bypass` cookie skips the
cache: it keeps its cookies, is rendered fresh and answered `private, no-store`, and is never
stored. Set the cookie when an author starts a preview, and clear it when they stop. A `GET`
or `HEAD` with the token in the `x-prerender-revalidate` header reaches your app on every edge,
is rendered fresh and answered `private, no-store`, and clears the path's entry, so the next
request fills it again. No edge refills the entry from the revalidating request itself: the
Cloudflare gateway renders it outside its cache and purges the path, and behind CloudFront or
the load balancer your app writes a purge of the path for the edge to clear. Both names are
Vercel's, and the token is compared in constant time.

## What each edge does

| Edge | Caches | A revalidation |
| --- | --- | --- |
| Cloudflare | the cached routes of the table, for `GET` requests without `Authorization`, keyed by host, release and the allowed query | reaches the edge from the response that made it, and is awaited before a write is answered; it is also recorded for the origin's cloud, which clears its own cache |
| CloudFront | every response that allows it, keyed by every query parameter | recorded in the app's tag table and cleared by the tag invalidator within moments; CloudFront cannot mark an entry stale, so both kinds clear it |
| Google Cloud load balancer | every response that allows it, keyed by every query parameter | cleared from Cloud CDN by the service itself; both kinds clear the entry |
| No edge | nothing | nothing |

Redirects and header rules are applied by your app on every edge. On Cloudflare the gateway
answers the redirects itself.

Some of the route table is applied only where the edge can do it:
- `allowQuery` keys the cache on Cloudflare only. CloudFront and the load balancer key on
  every parameter, which splits the cache more but never serves the wrong page.
- The bypass cookie is checked before the cache on Cloudflare only. CloudFront keeps a request
  with any `__prerender_bypass` cookie apart from the published page, and the load balancer
  keys on its value, so a preview reaches your app unless a request with another value already
  filled that entry.
- The revalidate header is checked by your app. CloudFront gives the request a cache key no
  other request shares, and the load balancer bypasses its cache for it, so it always reaches
  your app.
- `basePath` is applied by your app when it matches patterns.
- A container app is given no route table.
