By the end of this page a Next.js app is running in your AWS account on a hostname you own, and
`ocel deploy` is the only command it takes.

## Before you start

| You need | Why |
| --- | --- |
| Node 20.9 or newer | Next.js 16 needs it, and Ocel builds the app with it |
| An AWS account, with credentials in your shell | The app runs there, and Ocel provisions with those credentials |
| A domain you can add DNS records to | The app answers on a hostname you own |

Check the credentials are visible:

```bash
aws sts get-caller-identity
```

## Install

```bash
curl -fsSL https://ocel.dev/install.sh | sh
ocel --version
```

[Homebrew and npm](/docs/cli#install) install the same binary.

## Deploy

Ocel needs Next.js 16.2.10 or later.

```bash
npx create-next-app@latest my-app
cd my-app
ocel deploy
```

There's nothing to set up first: the deploy asks for what the project is missing, one question
at a time.

1. `Set up a project here? [y/N]`: it writes `ocel.config.ts` and adds the `ocel` package.
2. `Where should my-app deploy?`: pick `aws`.
3. `Add this to ocel.config.ts:` followed by `domains: { production: "my-app.example.com" },`.
   Save it with a hostname on your domain, then press Enter.
4. `Run ocel bootstrap production now? [y/N]`: it sets up the infrastructure every project in
   the account shares, once.

Answer no to any of them and nothing changes; the deploy names the command to run when you're
ready. Then it builds and provisions, prints the DNS records for your hostname and waits up to 15
minutes while you add them, and prints the URL: that is your app, in your account.

Every resource Ocel creates is keyed on the slug, so keep it once you've deployed. In a script or
in CI nothing is asked, so run the setup steps first:

```bash
ocel init --provider aws
# add domains.production to ocel.config.ts
ocel bootstrap production --yes
ocel deploy --yes
```

## Put Cloudflare in front

This deploy runs behind CloudFront, the default edge. For Next.js, Cloudflare in front of AWS is
the [recommended setup](/docs/frameworks/nextjs#recommended-cloudflare-in-front-of-aws): it
serves partial prerendering and edge-runtime code from the edge, and it is the most tested.

| You need | Why |
| --- | --- |
| Your domain's zone on Cloudflare, with SSL mode **Full (strict)** | Cloudflare answers on it, and Ocel writes the DNS records there itself |
| `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in your shell | Ocel deploys the worker and records with them; the token's permissions are in [Cloudflare edge](/docs/providers/cloudflare#setup) |

Add the edge and its DNS to the provider:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import { cloudflareDns } from "ocel/dns";
import { cloudflare } from "ocel/edge";
import awsProvider from "ocel/providers/aws";

export default defineConfig({
  slug: "my-app",
  provider: awsProvider({ edge: cloudflare(), dns: cloudflareDns() }),
  domains: { production: "my-app.example.com" },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": { "aws": { "edge": "cloudflare", "dns": "cloudflare" } },
  "domains": { "production": "my-app.example.com" }
}
```

```bash
ocel deploy
```

## Change something and deploy again

Edit `app/page.tsx`, then:

```bash
ocel deploy
```

Traffic moves to the new deployment. The previous ones are kept:

```bash
ocel promotions ls
ocel rollback
```

## Preview a branch

A preview needs a wildcard to be served under. Add one beside the production hostname:

```ts title="ocel.config.ts"
domains: {
  production: "my-app.example.com",
  preview: "*.my-app-previews.com",
},
```

Behind Cloudflare, its free certificate covers one label below a zone, so a wildcard in a zone
of its own needs nothing more. A deeper one, such as `*.preview.example.com`, needs Cloudflare's paid
[Advanced Certificate Manager](https://developers.cloudflare.com/ssl/edge-certificates/advanced-certificate-manager/).

```bash
git switch -c checkout
ocel preview
```

The first preview offers to run `ocel bootstrap preview`. The preview is a full deployment beside
production, on its own hostname under the wildcard. `ocel preview rm` tears it down and leaves
production alone. [`ocel preview`](/docs/cli/preview) covers names, CI and persistent previews.

## Clean up

```bash
ocel projects destroy
```

It asks you to type the project name, then removes the project's apps, resources and hostnames from
production and every preview, and nothing else. The shared infrastructure stays for other
projects. [`ocel projects`](/docs/cli/projects) lists what is still deployed on it; remove it once
nothing is:

```bash
ocel bootstrap destroy production
ocel bootstrap destroy preview
```
