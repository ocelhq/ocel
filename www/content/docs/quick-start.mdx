By the end of this page a Next.js app is running in your AWS account, on a hostname you own.

## Before you start

| You need | Why |
| --- | --- |
| Node 20.9 or newer | Next.js 16 needs it, and Ocel builds the app with it |
| An AWS account, with credentials in your shell | The app runs there, and Ocel provisions with those credentials |
| A domain you can add DNS records to | CloudFront, which serves the app, answers on a hostname you own |

Check the credentials are visible:

```bash
aws sts get-caller-identity
```

## Install

```bash
curl -fsSL https://ocel.dev/install.sh | sh
ocel --version
```

[Homebrew and npm](/docs/cli#install) install the same binary.

## Deploy

```bash
npx create-next-app@latest my-app
cd my-app
ocel deploy
```

Ocel needs Next.js 16.2.10 or later. The first deploy sets up what the project is missing, asking
before each step:

1. **The config.** It asks where `my-app` should deploy. Pick `aws`. It writes `ocel.config.ts`
   and adds the `ocel` package to your dependencies.
2. **The hostname.** It prints the line to add to `ocel.config.ts` and waits for you to save it.
   Use a hostname on your domain.
3. **The shared infrastructure.** The account has none yet, so it offers to run
   `ocel bootstrap production`. Later deploys, and other projects, reuse it.

Answer no to any step and the deploy stops and names the command to run when you're ready.

Then it builds and provisions. The hostname needs DNS records: the deploy prints them and waits
up to 15 minutes while you add them at your DNS provider. If the domain's zone is in Route 53,
add `dns: route53()` and Ocel writes them itself. The config ends up like this:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import awsProvider from "ocel/providers/aws";
import { route53 } from "ocel/providers/aws/dns";

export default defineConfig({
  slug: "my-app",
  provider: awsProvider({ dns: route53() }),
  domains: { production: "my-app.example.com" },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": { "aws": { "dns": "route53" } },
  "domains": { "production": "my-app.example.com" }
}
```

Every resource Ocel creates is keyed on the slug, so keep it once you've deployed.

The deploy prints the URL when it finishes. Open it: that is your app, in your account.

In a script or in CI nothing is asked, so set the project up first:

```bash
ocel init --provider aws
# add domains.production to ocel.config.ts
ocel bootstrap production --yes
ocel deploy --yes
```

## Change something and deploy again

Edit `app/page.tsx`, then:

```bash
ocel deploy
```

Traffic moves to the new deployment. The previous ones are kept:

```bash
ocel promotions ls
ocel rollback
```

## Preview a branch

A preview needs a wildcard to be served under. Add one beside the production hostname:

```ts title="ocel.config.ts"
domains: {
  production: "my-app.example.com",
  preview: "*.preview.example.com",
},
```

```bash
git switch -c checkout
ocel preview
```

The first preview offers to run `ocel bootstrap preview`. The preview is a full deployment beside
production, on its own hostname under the wildcard. `ocel preview rm` tears it down and leaves
production alone. [`ocel preview`](/docs/cli/preview) covers names, CI and persistent previews.

## Clean up

```bash
ocel destroy production
```

It asks you to type the project name, then removes the project's apps, resources and hostnames,
and nothing else. The shared infrastructure stays for other projects. Remove it once nothing is
deployed on it:

```bash
ocel bootstrap destroy production
ocel bootstrap destroy preview
```
