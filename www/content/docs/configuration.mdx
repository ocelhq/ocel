Every option lives in one config at the root of your project. `ocel init` writes it as
`ocel.config.ts` in a project built with node, and as `ocel.json` in any other.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import awsProvider from "ocel/providers/aws";

export default defineConfig({
  slug: "my-app",
  provider: awsProvider(),
  apps: [{ name: "web", path: "." }],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": "aws",
  "apps": [{ "name": "web", "path": "." }]
}
```

Both are the same document, and every field, default and error on this page is the same in
either.

`slug` is the project's identity in your provider account. Every stack and resource ocel
creates is keyed on it, so changing it forks a new project.

`provider`, `edge` and `dns` each name one choice. In `ocel.config.ts` it is a function that
takes the choice's options, such as `awsProvider({ region: "us-east-1" })`. In `ocel.json` it
is an object keyed by its identifier and containing its options, such as
`{ "aws": { "region": "us-east-1" } }`, or the identifier alone when it needs none, as `"aws"`
is above. Each edge takes options of its own: `tunnel` is the Cloudflare edge's, and
CloudFront, API Gateway and the load balancer take none.

One project reads one config: a directory containing two of `ocel.config.ts`, `ocel.json`,
`ocel.yaml` and `ocel.yml` is refused, and so is one containing two forms of the same target,
such as `ocel.vps.config.ts` and `ocel.vps.json`.

## TypeScript

`ocel.config.ts` compiles to the same document as `ocel.json`, so nothing else in ocel knows
which form you chose. `defineConfig` comes from `ocel/config`, each provider from
`ocel/providers/<name>`, the Cloudflare edge from `ocel/edge` and Cloudflare DNS from
`ocel/dns`. An edge or DNS that belongs to one provider comes from beside it, such as
`cloudfront` from `ocel/providers/aws/edge`.

### What it costs

Reading it needs `node` on `PATH`, and the `ocel` package as a dependency. Every command that
reads the config — `ocel deploy`, `ocel dev`, `ocel env`, `ocel destroy` — bundles and runs the
file first, on every machine and in every CI job. A go, rust or python project would pay for
a node toolchain it otherwise does not have, which is why `ocel init` writes `ocel.json` for a
project not built with node.

### What it buys

The provider, edge, dns and [env source](/docs/env-sources) descriptors are functions, so your
editor knows which options each one takes as you type them.

Values may be computed, and `buildEnv` reads what the config itself needs while it is
evaluated — from the shell or from a `.env` beside the config — through a schema of your own,
so a missing or malformed variable is named before anything is provisioned:

```ts title="ocel.config.ts"
import { buildEnv, defineConfig } from "ocel/config";
import vpsProvider from "ocel/providers/vps";
import { z } from "zod";

const ssh = buildEnv({
  DEPLOY_HOST: z.string().min(1),
  DEPLOY_PORT: z.coerce.number().default(22),
});

export default defineConfig({
  slug: "my-app",
  provider: vpsProvider({ ssh: { host: ssh.DEPLOY_HOST, port: ssh.DEPLOY_PORT } }),
  apps: [{ name: "web", path: "." }],
});
```

`ocel.json` reaches the same variables with `${DEPLOY_HOST}`, unchecked and as a string.

A [transform](/docs/transforms) is a module path, not a value the config imports, so it
works the same from either form.

## JSON

`ocel.json` needs no node: the CLI reads it on its own. `ocel init --format json` writes it in
a project built with node too.

The `$schema` line is what your editor completes and validates against. It is one URL, and
it always describes the latest release. A key the CLI you run does not know is refused with
an error that names it.

The file is JSON with comments and trailing commas allowed, so a variant you are not using
can sit beside the one you are.

## YAML

The same document can be written as YAML, in `ocel.yaml` or `ocel.yml`. Every field,
default and error is the one this page describes. `ocel init --format yaml` writes it.

```yaml title="ocel.yaml"
# yaml-language-server: $schema=https://ocel.dev/schema/ocel.schema.json
slug: my-app
provider: aws
apps:
  - name: web
    path: .
```

The first line is what your editor completes and validates against. Anchors and merge keys
expand before ocel reads the document, so apps that share settings can share them once.

## Variables

Any string may interpolate an environment variable with `${NAME}`. The value comes from
your shell, or from a `.env` beside the config. A name nothing sets refuses the deploy
rather than deploying a config with a hole in it. Write `$${` where a literal `${` belongs.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import vpsProvider from "ocel/providers/vps";

export default defineConfig({
  slug: "my-app",
  provider: vpsProvider({ ssh: { host: "${DEPLOY_HOST}", user: "deploy" } }),
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "vps": { "ssh": { "host": "${DEPLOY_HOST}", "user": "deploy" } }
  }
}
```

This is for values that differ per machine, not for secrets. Secrets belong in
[variables](/docs/environments), which are stored in your own account.

The one secret the CLI itself needs, the password `registry` pushes with, is written as
the placeholder alone and read from your shell, then the project's `.env`, when the push
authenticates, so the config says where the secret comes from and never contains it:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  registry: { server: "ghcr.io/acme", password: "${REGISTRY_TOKEN}" },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "registry": { "server": "ghcr.io/acme", "password": "${REGISTRY_TOKEN}" }
}
```

Anything else there is refused: the secret itself, a bare `REGISTRY_TOKEN`, text around the
placeholder, or in `ocel.config.ts` a value read with `buildEnv`.

## ocel.lock

`ocel lock` writes `ocel.lock` beside the config: this CLI's version, and the sha256 of
every provider archive of that release on every platform. Commit it. Every machine and
every CI run then fetches the same bytes, and a CLI of another version is refused until
you run `ocel lock` again.

A project with no `ocel.lock` gets one the first time a command fetches its providers.
A `--dry` run writes none: with no `ocel.lock`, or one another version wrote, it pins the
providers for that run alone.

## discovery.paths

The folders discovery runs to collect your resource declarations.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  discovery: { paths: ["packages/*/infra"] },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "discovery": { "paths": ["packages/*/infra"] }
}
```

Default: `infra` next to the config file. Setting `discovery.paths` replaces it.

A path is relative to the config file and may be a glob. It names a folder, and every
source file under that folder runs during discovery.

Each folder's language is the one the source files in it are written in, not the one a
manifest names: `.go` is go, `.py` is python, `.rs` is rust, and `.ts`, `.tsx`, `.js`,
`.jsx`, `.mjs` or `.cjs` is js. A folder containing two of them is an error.

## framework

What an app is built with, when ocel is not to read it off the app's own directory.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  apps: [{ name: "web", path: ".", framework: "next" }],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "apps": [{ "name": "web", "path": ".", "framework": "next" }]
}
```

One of `node`, `next`, `go`, `python` or `rust`. Left off, ocel reads the app's directory: a
`package.json` that names `next` as a dependency or sits beside a `next.config.*` is next,
a `package.json` on its own is node, a `go.mod` is go, a `pyproject.toml` or
`requirements.txt` is python, and a `Cargo.toml` is rust. A `Cargo.toml` beside a
`package.json`, `pyproject.toml` or `requirements.txt` builds that app's native extension,
so the app is node, next or python.

On container compute only `next` may be named, or is read off the directory; the other
frameworks are serverless-only, and a container app declaring one is refused.

A rust app's crate builds one binary. ocel compiles it with `cargo` for the app's `arch`
as a static musl binary, so the matching target must be installed:
`rustup target add x86_64-unknown-linux-musl` or `aarch64-unknown-linux-musl`.

That is enough for a pure-Rust crate. A crate that compiles C, through `ring`, `aws-lc-rs` or
`openssl-sys`, also needs a musl C cross toolchain for the target, most of all for `arm64`
built on an x86_64 machine. Name its compiler with `CC_aarch64_unknown_linux_musl`, and its
linker in `.cargo/config.toml`:

```toml title=".cargo/config.toml"
[target.aarch64-unknown-linux-musl]
linker = "aarch64-linux-musl-gcc"
```

or with `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_LINKER`. ocel links with `rust-lld` only when
neither names a linker for the target.

## arch

The processor architecture an app's functions or container image are built for.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  apps: [{ name: "web", path: ".", arch: "arm64" }],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "apps": [{ "name": "web", "path": ".", "arch": "arm64" }]
}
```

Either `x86_64` or `arm64`. Left off, it is what your provider runs the app on. A provider
that cannot run the one you name refuses the deploy before anything is built.

## minInstances and maxInstances

How many instances of a container app run: at least `minInstances`, however quiet it is, and
at most `maxInstances`, however busy.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  apps: [
    { name: "api", path: "api", compute: "container", minInstances: 2, maxInstances: 10 },
  ],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "apps": [
    { "name": "api", "path": "api", "compute": "container", "minInstances": 2, "maxInstances": 10 }
  ]
}
```

Both are whole numbers: `minInstances` from 0, `maxInstances` from 1, and `minInstances` no
more than `maxInstances`. Left off, `minInstances` is 1 and `maxInstances` is `minInstances`,
or 1 when that is 0. A container app that sets neither runs exactly one instance on every
provider, and never scales.

Each instance kept running is billed whether it serves a request or not. The two numbers are
set once per app, with no override for a tier or a preview, so every preview keeps the same
`minInstances` running as production does, and each one is billed for them.

What the two numbers do depends on the provider:

| Provider | Between the two |
| --- | --- |
| AWS | The ECS service starts at `minInstances`. When `maxInstances` is higher, it adds tasks when the load balancer counts more than 1,000 requests a minute per task, and removes them when the count falls. `minInstances` must be at least 1. |
| Google Cloud | Cloud Run's `min-instances` and `max-instances`. Cloud Run scales on concurrent requests, and a `minInstances` of 0 lets the service scale to zero. |
| VPS | A box runs one container per app, so both must be 1 or left off. |

A serverless app scales itself, so either field on one is refused. The same goes for an app
whose provider runs it on functions because it names no `compute`.

## health

The path a container app is checked on before a release of it serves traffic. Any 2xx
answer means it is up.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  apps: [{ name: "api", path: "api", compute: "container", health: { path: "/health" } }],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "apps": [
    { "name": "api", "path": "api", "compute": "container", "health": { "path": "/health" } }
  ]
}
```

The path starts with `/` and has no query or fragment. A path you set is always the one
checked. Left off, the provider picks one:

| Provider | With no `health.path` |
| --- | --- |
| AWS | The load balancer checks `/`. |
| Google Cloud | Cloud Run's startup probe requests `/`. |
| VPS | The first deploy of the app finds the path by probing, and later deploys reuse it. See [Health checks](/docs/providers/vps#health-checks). |

A serverless app runs no process to check, so `health` on one is refused.

## bindings

A resource the code declares is provisioned in your account, unless `bindings` names what it
binds to instead. Keyed by resource type, then by the name the code declares.

A record your own infrastructure published, with `ocel bindings set` or the SST and Pulumi
packages, is written `"@"` and the name it was published under:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  bindings: { postgres: { analytics: "@warehouse" } },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "bindings": { "postgres": { "analytics": "@warehouse" } }
}
```

Or write the record itself. A postgres takes its connection string whole, which keeps the
`sslmode`, `options` and pooler parameters a hosted database needs:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  bindings: { postgres: { orders: { url: { $env: "ORDERS_DATABASE_URL" } } } },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "bindings": { "postgres": { "orders": { "url": { "$env": "ORDERS_DATABASE_URL" } } } }
}
```

or its parts, keyed by the tier it serves:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  bindings: {
    postgres: {
      orders: {
        production: {
          host: "db.abcdefghijkl.supabase.co",
          database: "postgres",
          username: "postgres",
          password: { $env: "SUPABASE_DB_PASSWORD" },
          tls: { mode: "verify-full", ca: { $env: "SUPABASE_CA" } },
        },
      },
    },
  },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "bindings": {
    "postgres": {
      "orders": {
        "production": {
          "host": "db.abcdefghijkl.supabase.co",
          "database": "postgres",
          "username": "postgres",
          "password": { "$env": "SUPABASE_DB_PASSWORD" },
          "tls": { "mode": "verify-full", "ca": { "$env": "SUPABASE_CA" } }
        }
      }
    }
  }
}
```

A binding keyed by `production` or `preview` serves that tier alone, and the other provisions
its own resource as usual. `ocel dev` always runs its own. A bucket binds to one in a store you
already run: see [Bucket](/docs/sdk/bucket#a-bucket-in-a-store-you-already-run).

`{ "$env": "NAME" }` is a [variable](/docs/environments), set with `ocel env set` for each tier
and environment, and it is the only way a password, a connection string, a CA or a key reaches a
binding. `${NAME}` in the same file is read from your shell when the config loads, and belongs to
the values that are not secret. Each `$env` a binding reads is required like one your code declares:
the deploy stops and names the `ocel env set` that fills it. The variables editor shows it
grouped under the binding. The app never receives it, and a name both your code declares and a
binding reads is refused.

Nothing written inline is provisioned, so the deploy checks it instead. It connects to a postgres
and compares its major version with the one the code declares, and it checks a bucket's access,
CORS and policy against what the code asks of it. A binding that fails the check stops the deploy
before anything is built.

A preview per pull request can bind a database branch of its own. Bind the database to a
published record instead of writing it inline:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  bindings: { postgres: { orders: "@orders" } },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "bindings": { "postgres": { "orders": "@orders" } }
}
```

Publish production's record once, with `ocel bindings set < orders.json`, and publish none for
the preview tier as a whole. A record published with `--environment` serves that one preview,
and can be published before the preview has ever deployed. A preview with no record of its own
falls back to the record published for the preview tier as a whole, when one exists, and its
deploy is refused only when neither exists. With no tier-wide record, a preview that was never
given its own is refused rather than reaching a database another preview uses.

In CI, name each preview after its pull request, and on every run create its branch if it is
missing and publish it before the deploy:

```yaml title=".github/workflows/preview.yml"
- run: |
    NAME=pr-${{ github.event.number }}
    neonctl branches get "$NAME" > /dev/null 2>&1 || neonctl branches create --name "$NAME"
    URL=$(neonctl connection-string "$NAME")
    jq -n --arg url "$URL" '{name: "orders", source: "neon", postgres: {url: $url}}' |
      ocel bindings set --preview --environment "$NAME"
- run: ocel preview up pr-${{ github.event.number }}
```

## lifecycle

Commands `ocel deploy` runs on your machine at points of a deploy. `preBuild` is the first: a
command that runs once per deploy, after your infrastructure is provisioned and before any app is
built. It is where a database migration goes.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  lifecycle: { preBuild: "pnpm drizzle-kit migrate" },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "lifecycle": { "preBuild": "pnpm drizzle-kit migrate" }
}
```

Written as an object, it takes four fields:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";

export default defineConfig({
  slug: "my-app",
  apps: [{ name: "web", path: "web" }],
  lifecycle: {
    preBuild: {
      command: "pnpm migrate",
      app: "web",
      previews: "persistent",
      timeout: "15m",
    },
  },
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "apps": [{ "name": "web", "path": "web" }],
  "lifecycle": {
    "preBuild": {
      "command": "pnpm migrate",
      "app": "web",
      "previews": "persistent",
      "timeout": "15m"
    }
  }
}
```

| Field | Means |
| --- | --- |
| `command` | The shell command to run. |
| `app` | The app whose variables the command also receives, and whose directory it runs from. Left off, the command runs from the project directory and receives the bindings alone. |
| `previews` | Which previews run it: `persistent` (the default), `all` or `none`. Production always runs it. |
| `timeout` | How long it may run, as a duration such as `90s` or `15m`. Left off, 30 minutes. Past it, the command is stopped with everything it started. |

The command reads your resources the way your code does. Every binding of the project is in
`OCEL_LIVE_DIR`, forwarded to the deployed resource, so `postgres("main").connectionString` in
`drizzle.config.ts` is the deployed database, exactly as it is under `ocel run`. A provider that
forwards no port runs the command without bindings and the deploy says so, as it does for a
resource neither a port nor the provider's proxy reaches, such as a topic. A bucket the provider owns is
reached through that proxy, which the command finds at `OCEL_RUNTIME_ADDRESS` as your code does when
deployed, and a page that reads a bucket while it builds is built the same way. When the provider refuses a forward, because the
database is not running or nothing is deployed yet, the deploy stops before the command runs and
says why. Its output streams into the deploy.

A command that exits non-zero, or runs past its `timeout`, stops the deploy before anything is built.
The infrastructure stays as provisioned, nothing is promoted, and the release that was serving keeps
serving.

It never runs on `ocel rollback` or `ocel env set`. `ocel deploy --dry` lists it in the plan and runs
nothing. `--prebuilt` builds nothing and leaves provisioning to the deploy itself, so it skips the
command and says so: run it yourself first with `ocel run --env`.

### Previews

An ephemeral preview, the kind `ocel preview up` makes for a branch, gets no infrastructure of its own.
It shares the preview tier's databases with every other ephemeral preview, so a migration run from one
changes what all of them read. `persistent`, the default, runs the command for production and for
persistent previews, which have their own. `all` runs it for every preview, which suits a preview
bound to a database branch of its own (see [bindings](#bindings)). `none` leaves previews alone.

### Expand and contract

Between the command and the promotion, the release that is serving runs against the new schema. This
holds for a migration run after the build too. Write migrations that the running release survives:
expand first (add the column, the table or the index, nullable or defaulted), deploy code that uses
it, and contract in a later deploy (drop what nothing reads). A rename is an add, a copy and a drop
across three deploys.

### npm's prebuild is a different thing

npm and yarn 1 run a `prebuild` script from `package.json` before the `build` script, once per app,
with the build's environment. `lifecycle.preBuild` runs once per deploy, with the deployed bindings.
They do not replace each other. When both are set, both run, and the deploy warns once so a migration
is not run twice by accident. Move the command out of the `prebuild` script when only
`lifecycle.preBuild` should run it.

### By hand

`ocel run --env production -- pnpm drizzle-kit migrate` opens the same forwards against the deployed
environment and runs a command of your choosing with its bindings. See [`ocel run`](/docs/cli/run).

## Another config per target

A file named `ocel.<target>.config.ts`, or `ocel.<target>.json`, is the same project deployed
somewhere else — a box of your own beside the cloud you ship to. Point any command at one with
`--config` or `OCEL_CONFIG`:

```bash
ocel deploy --config ocel.vps.config.ts
```
