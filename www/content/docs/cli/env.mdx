---
title: ocel env
description: Manage this project's variable values.
---

```bash
ocel env ls
ocel env set LOG_LEVEL=debug
ocel env ui --preview
```

Values live in your own account, one store per deployed tier. Every command addresses
production unless you pass `--preview`. `--folder /web` addresses the value in one variables
folder, and `--environment pr-12` narrows a preview command to the preview whose identity is
`pr-12`: the first column of `ocel preview ls`, not the label.

| Command | What it does |
| --- | --- |
| `ls` | List values without revealing them, with the env source each one came from. |
| `get <KEY>` | Inspect a value; `--reveal` prints it. |
| `set <KEY=VALUE>...` | Set values. |
| `rm <KEY>` | Remove a value. |
| `ref <KEY>` | Read a value stored under another project, folder or key: `--target-project`, `--target-folder`, `--target-key`. |
| `refs <KEY>` | List the references to a value. |
| `history <KEY>` | List a value's versions. |
| `ui` | Open the variable editor in your browser. |
| `source` | Show where the tier reads its values from, when it last synced and the last error, and what dev reads. |
| `sync` | Read the env source the tier's last deploy registered into its values now. |

When a tier reads from an [env source](/docs/env-sources) other than ocel's own store,
`set` writes a value that source owns into the source when its `write` allows it, and
otherwise refuses and links to where to change it there. `rm` always refuses, because ocel
never deletes a key from an env source. The
dev tier's values are read on your machine by `ocel dev` and `ocel run`, so no `ocel env`
command addresses them.

## Values in the build

When `ocel deploy` builds an app as functions, a build step that runs the app's own code gets
every value the app resolves, so code that reads one while the app builds works whatever the
value's class. For a Next app that is your `build` script, such as a route module that creates
its API client at import; for a Rust app it is `cargo build`, with your `build.rs` and proc
macros. A Go, Python or plain Node app's build runs none of your code, so it gets none. Nor
does the code in a [discovery folder](/docs/configuration#discoverypaths): `ocel` runs it to
find what the app declares, before any value resolves.

A plaintext value is in the build's environment. A sensitive or secret value is not: the build
reads it from a file in a private directory on the deploying machine, outside the project,
which the SDK reads by itself and which is removed when the build ends, failed or not, and when
an interrupt makes `ocel` exit. A Next build that reads one needs Node 20.16+ or 22.3+ where
its `build` script runs, and is refused before it starts on an older one. A value the deploy
resolved wins over the same key in your shell, and the build's output shows `[secret]` where
it printed a sensitive or secret value.

Cargo reruns a `build.rs` only when something it watches changes, so a changed value reaches
one only if it watches the value: print `cargo:rerun-if-env-changed=<KEY>` for a plaintext
value, and for a sensitive or secret one `cargo:rerun-if-env-changed=OCEL_LIVE_DIR`, whose
path is new on every build, or `cargo:rerun-if-changed` with the path of the value's file.

An app built as an image gets its sensitive and secret values and the bindings of the
resources it uses, and none of its plaintext values: a plaintext value would have to be an
`ARG` or `ENV`, which an image keeps. The deploy warns for each such app, naming the plaintext
values it declares. The values reach the build as build secrets, which never enter a layer, an
`ARG`, an `ENV` or the image's history. `ocel build` reads no tier, so its output, and an
`ocel deploy --prebuilt` of it, was built with none of the app's values.

A binding reaches the build over a port `ocel` forwards on your machine's `127.0.0.1`, so the
step that reads the values runs on the host network, and the docker daemon must share your
machine's network. A daemon on another machine, which `DOCKER_HOST` can point at, or one in a
virtual machine, such as Docker Desktop's, has a `127.0.0.1` of its own, and a build step there
cannot reach the forwards. The daemon must also allow the `network.host` entitlement, which its
builder does unless `daemon.json` sets `"builder": { "entitlements": { "network-host": false } }`.

A railpack build needs no change. Its `build` step finds each value as a file in
`/run/ocel-live`, which the SDK reads by itself. No other step has the values in a file or in
its environment, or runs on the host network. The build step runs again whenever a value
changes.

A Dockerfile declares `ARG OCEL_LIVE_HASH` in the stage that reads the values, mounts each
value it needs as a secret named after its key, sets `OCEL_LIVE_DIR` for the command that
reads it, and runs that command on the host network:

```dockerfile title="Dockerfile"
ARG OCEL_LIVE_HASH
RUN --mount=type=secret,id=OCEL_RESOURCE_POSTGRES_main,target=/run/ocel-live/OCEL_RESOURCE_POSTGRES_main,required=false \
    --network=host \
    OCEL_LIVE_DIR=/run/ocel-live pnpm run build
```

A bucket is read through the provider's binding proxy, which listens on your machine's
`127.0.0.1`. A railpack build step has its address and session token in its environment, as
`OCEL_RUNTIME_ADDRESS` and `OCEL_SESSION_TOKEN`. A Dockerfile mounts both as secrets into the
command's environment, which needs Dockerfile syntax 1.10 or later:

```dockerfile title="Dockerfile"
ARG OCEL_LIVE_HASH
RUN --mount=type=secret,id=OCEL_RUNTIME_ADDRESS,env=OCEL_RUNTIME_ADDRESS,required=false \
    --mount=type=secret,id=OCEL_SESSION_TOKEN,env=OCEL_SESSION_TOKEN,required=false \
    --network=host \
    pnpm run build
```

A secret mount does not change a step's cache key, so without the `ARG` docker reuses the
cached step after a value changes, and the build output keeps what it rendered from the old
value. `OCEL_LIVE_HASH` changes whenever a value does. It is a hash keyed with a random key
kept in your ocel config directory, which `docker history` shows, and which nobody can test a
guessed value against without that key.

Never copy a value into an `ARG` or `ENV`, or write it to a file the image keeps: `docker
history` and the image's layers show those.

Whatever a prerendered page renders from a value is in the build output, and stays there
until the next deploy. Rotating a secret changes what the running app reads, but not a page
that was built from it.
