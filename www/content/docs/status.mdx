Ocel deploys real apps into your own account, but it is early: expect rough edges, and expect
things to change.

## What can change

Anything: config fields, CLI flags and output, SDK APIs, and the infrastructure a deploy
creates. Until a stable release, a change ships as a clean break. The old way stops working in
the same release the new one arrives, with no deprecation period and no migration step.

## How to build on it

- **[Pin](/docs/cli#installer) the CLI and the SDK to the same release.** An SDK works only with the CLI of its own
  release, and a mismatch refuses to build ([`sdk.version_mismatch`](/docs/errors/sdk.version_mismatch)).
  Pinning both means an upgrade happens when you choose it.
- **Read the [release notes](https://github.com/ocelhq/ocel/releases) before you upgrade.** A breaking
  change is announced there, and nowhere else warns you.
- **Start with an app you can redeploy from scratch.** What a deploy creates lives in your own
  account, so if a release changes it, `ocel destroy` and a fresh deploy start you over.

## Telling us what broke

Bugs and rough edges go in [GitHub issues](https://github.com/ocelhq/ocel/issues/new/choose).
Include the output of `ocel --version` and the provider you deploy to, so we can reproduce it.

Report a security issue privately, as [SECURITY.md](https://github.com/ocelhq/ocel/blob/main/SECURITY.md)
describes, never in a public issue.
