```bash
pnpm add -D @ocel/sveltekit
```

```ts tab="SvelteKit 3" title="vite.config.ts"
import ocel from "@ocel/sveltekit";
import { sveltekit } from "@sveltejs/kit/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [sveltekit({ adapter: ocel() })],
});
```

```js tab="SvelteKit 2.31+" title="svelte.config.js"
import ocel from "@ocel/sveltekit";

export default { kit: { adapter: ocel() } };
```

```bash
ocel deploy
```

Ocel recognises the app by its `@sveltejs/kit` dependency and runs its `build` script. Every
route renders in one function. Prerendered pages and `static/` are served beside it. Files under
`/_app/immutable/` are cached for a year, and everything else is revalidated on each request, so
an open tab sees a new deployment through `/_app/version.json`.

## How ocel finds the app

A directory is a SvelteKit app when its `package.json` lists `@sveltejs/kit` in `dependencies` or
`devDependencies`. The `svelte.config.js` and `vite.config.ts` aren't read, so the dependency has
to be there.

Within one `package.json`, SvelteKit wins over node, so a server file such as `src/server.ts`
beside the app does not make it a node app. A `package.json` that also depends on `next` matches
two frameworks, and ocel deploys neither until the app sets `framework`.

With no `apps` in your config, the project root is deployed as the SvelteKit app. A
`pyproject.toml` or `go.mod` beside it is fine while it holds no app. If it holds a
[Python](/docs/frameworks/python#how-ocel-finds-the-app) or
[Go](/docs/frameworks/go#how-ocel-finds-the-app) app, ocel cannot tell which to deploy and asks
you to list the app under `apps` with `framework: "sveltekit"`.

## Containers

On `compute: "container"`, and on a [VPS](/docs/providers/vps), which runs only containers, the
image runs your `start` script:

```json title="package.json"
{
  "scripts": { "build": "vite build", "start": "node build" }
}
```

## Environment variables

On SvelteKit 3, declare variables with `defineEnvVars` from `ocel/env/sveltekit` in your
[discovery folder](/docs/configuration#discoverypaths), and re-export them from `src/env.ts`:

```ts title="resources/env.ts"
import { defineEnvVars } from "ocel/env/sveltekit";
import * as v from "valibot";

export const variables = defineEnvVars({
  STRIPE_KEY: { class: "sensitive", description: "Stripe key" },
  PUBLIC_API_URL: { class: "plain", public: true, schema: v.pipe(v.string(), v.url()) },
});
```

```ts title="src/env.ts"
export { variables } from "../resources/env";
```

Ocel reads `class` and `folders`. SvelteKit reads `public`, `static`, `schema` and `description`,
and generates the `$app/env/*` types. Ocel writes nothing into your `tsconfig.json`.

`defineEnvVars` refuses:

| Declaration | Why |
| --- | --- |
| `public: true` on a class other than `plain` | SvelteKit hands public values to the browser. |
| `class: "secret"` | SvelteKit reads a value once, at startup, so a rotated secret never arrives. Use `sensitive`, or `defineEnv` from `ocel/env`, which reads it live. |
| `static: true` on `sensitive` | SvelteKit would inline the value into the server bundle. |
| `PUBLIC_OCEL_URL` | Ocel sets it. |

`PUBLIC_OCEL_URL`, in `$app/env/public`, is the URL the deployment is served from. An app served
on no hostname, reached only at its provider's own address, has no value for it.

A container's image build reads the app's `plain` values: Railpack's build step has them in its
environment, and a Dockerfile receives them as build arguments, so it declares an `ARG` for each
one `vite build` reads. `sensitive` values reach it only as build secrets.
