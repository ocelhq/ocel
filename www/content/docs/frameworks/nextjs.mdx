---
title: Next.js
description: Deploy a Next.js app.
---

```bash
ocel deploy
```

That is the whole setup. The CLI carries Ocel's Next.js adapter, so there is nothing to install
and nothing to add to `next.config`. It needs Next.js 16.2.10 or later. `ocel deploy` recognises
the app by a `next.config.*` or a `next` dependency and runs its `build` script with the adapter.

## Recommended: Cloudflare in front of AWS

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import { cloudflareDns } from "ocel/dns";
import { cloudflare } from "ocel/edge";
import awsProvider from "ocel/providers/aws";

export default defineConfig({
  slug: "my-app",
  provider: awsProvider({ edge: cloudflare(), dns: cloudflareDns() }),
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": { "aws": { "edge": "cloudflare", "dns": "cloudflare" } }
}
```

The app runs on AWS and Cloudflare serves it: a worker runs in front of the cache, so every
Next.js feature in the table below is served from the edge. It is the most tested setup: Next.js's
own [deployment adapter test suite](https://nextjs.org/docs/app/api-reference/adapters/testing-adapters)
runs against it, and the cases it still fails are listed in
[`tests/next-compat/baseline-manifest.json`](https://github.com/ocelhq/ocel/blob/main/tests/next-compat/baseline-manifest.json).

It needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in your environment and your domain's
zone on Cloudflare; see [Cloudflare edge](/docs/providers/cloudflare#setup) for the token's
permissions. Edge middleware and `runtime = "edge"` routes also need the Workers Paid plan. [Quick start](/docs/quick-start#put-cloudflare-in-front)
walks the switch from the default edge.

You can also keep CloudFront, the default: leave `edge` and `dns` off. CloudFront serves
everything except partial prerendering and edge-runtime code, which then
[run degraded](#on-cloudfront) or stop the deploy.

## What works

| Next.js feature | Cloudflare edge | CloudFront |
| --- | --- | --- |
| App Router and Pages Router, route handlers and API routes | Yes | Yes |
| Server Actions | Yes | Yes |
| Streaming | Yes | Yes |
| Static and prerendered pages, ISR with `revalidate` | Yes, cached at the edge | Yes, cached at the edge |
| `revalidatePath` and `revalidateTag` | Yes, purges the edge by tag | Yes, purges the edge by tag |
| `use cache` and `cacheComponents` | Yes | Yes |
| Partial prerendering (the static shell of a `cacheComponents` page) | Yes | [Degraded](#on-cloudfront) |
| `proxy.ts` and other Node.js middleware | Yes, in the app's function | Yes, in the app's function |
| Edge-runtime middleware and `runtime = "edge"` routes | Yes, on Workers Paid | [Degraded](#on-cloudfront) |
| `next/image` | Yes, through a shared optimizer | Yes, through a shared optimizer |
| Redirects, rewrites and headers in `next.config`, `basePath`, `i18n`, `trailingSlash` | Yes | Yes |
| Draft mode | Yes | Yes |

## On CloudFront

A deploy whose app uses something CloudFront does not serve is refused, naming the routes it
affects. Either move to the Cloudflare edge above, or accept the degraded behaviour with
`allowDegraded`:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import awsProvider from "ocel/providers/aws";

export default defineConfig({
  slug: "my-app",
  provider: awsProvider(),
  allowDegraded: ["ppr-resume", "edge-runtime"],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": "aws",
  "allowDegraded": ["ppr-resume", "edge-runtime"]
}
```

| Waived | What changes |
| --- | --- |
| `ppr-resume` | The shell and the resumed stream both come from the origin, so the shell no longer arrives first |
| `edge-middleware` | Middleware runs in the origin's function, so every request makes the round trip before it is routed |
| `edge-runtime` | Edge routes run in the origin's function, answering from one region |

## Functions

Each route runs in an AWS Lambda function. Routes are packed together until a function reaches
200 MiB, then the next starts, so a large app is split across several functions on its own.
Node.js middleware runs in the first function.

To serve every route from one image instead, set `compute: "container"` on the app
([container](/docs/configuration#container)).

## Caching

- Prerendered pages and ISR entries are cached at the edge. On CloudFront, cache misses for them
  go through [Origin Shield](/docs/providers/aws#cloudfront-origin-shield).
- `revalidatePath` and `revalidateTag` purge the edge by cache tag.
- `revalidate` does nothing on an edge-rendered route. The build warns which.
- Ocel installs its own cache handler. A build that sets `cacheHandler` or `cacheHandlers` is
  refused, as is one that sets `adapterPath`.
- For the production build, Ocel sets `cacheMaxMemorySize: 0`, so every function reads the shared
  cache rather than a copy of its own.
- `next/image` with a `loader` other than the default, or `unoptimized: true`, deploys no optimizer, and the build
  says so.

## Previews

A preview of a Next.js app is built and served like production. See
[`ocel preview`](/docs/cli/preview).

## Environment variables

Declare variables with `defineEnv` from `ocel/env/next`, in a file in your
[discovery folder](/docs/configuration#discoverypaths), where ocel looks for declarations. A key
with the `NEXT_PUBLIC_` prefix is public: Next inlines it into the browser bundle, so it must be
class `plain`. Declaring one as `sensitive` or `secret` is a type error, and refused at runtime.

```ts title="resources/env.ts"
import { defineEnv } from "ocel/env/next";
import { z } from "zod";

export const env = defineEnv({
  STRIPE_KEY: { class: "secret" },
  NEXT_PUBLIC_API_URL: { class: "plain", schema: z.string().url() },
});
```

Import `env` from that file wherever the app reads a variable, in server and client code alike:

```tsx title="app/page.tsx"
import { env } from "../resources/env";

export default function Page() {
  return <p>{env.NEXT_PUBLIC_API_URL}</p>;
}
```

In the browser, `env.NEXT_PUBLIC_API_URL` is parsed through its schema, and any other key throws,
saying it is server-only. The server and the edge read the same inlined value for a public key,
so a page renders the same on the server as in the browser. Groups work like they do in
`ocel/env`.

Next inlines the value when it builds, so `ocel env set` on a public key needs a rebuild; under
`ocel dev`, ocel restarts the dev server. `NEXT_PUBLIC_OCEL_URL` holds the URL the deployment is
served from, like `OCEL_URL`. Both come from the hostname the deploy serves the app on, so an app
served on none, such as one reached only at its provider's own address, gets neither. Ocel
writes nothing into your `tsconfig.json`.

## Link previews

Next.js resolves a relative `openGraph.images` or `twitter.images`, and the image an
`opengraph-image` or `twitter-image` file generates, against `metadataBase`. Social sites need
absolute image URLs to show a link preview.

When `metadataBase` is unset, Next.js falls back to the host in `VERCEL_PROJECT_PRODUCTION_URL`,
and to `http://localhost:3000` without it. Ocel sets that variable on a Next.js app, at build and
at runtime, to the host of `NEXT_PUBLIC_OCEL_URL`: the production hostname in production, the
preview's own hostname in a preview. Next.js reads it nowhere else. The build still warns that
`metadataBase` is not set, naming the host it used.

Set `metadataBase` yourself to silence the warning, to resolve relative `alternates` and
`openGraph.url` too (Next.js leaves those relative without one), or to give a URL to an app
served on no hostname of its own:

```tsx title="app/layout.tsx"
import type { Metadata } from "next";

export const metadata: Metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_OCEL_URL ?? "http://localhost:3000"),
};
```

`NEXT_PUBLIC_OCEL_URL` is set when the deploy serves the app on a hostname: one in
`domains.production` (see [`ocel domain`](/docs/cli/domain)), or for a preview, a
`domains.preview` or the preview domain from `ocel domain use --preview`. Under `ocel dev` it is
the local URL. An app reached only at its provider's own address gets neither variable, so its
images point at `localhost` until you give it a hostname or a literal `metadataBase`.
