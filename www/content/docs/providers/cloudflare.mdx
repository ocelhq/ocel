title: Cloudflare edge
description: Put an edge in front of any origin.
---

Cloudflare is an edge, not an origin: it fronts whichever provider runs your app.

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": "aws",
  "edge": "cloudflare",
  "apps": [{ "name": "web", "path": "." }]
}
```

The token and the account id come from `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the environment, not from the config.

On a [VPS](/docs/providers/vps) or [Google Cloud](/docs/providers/gcp), Cloudflare runs no
worker: it forwards each hostname to the origin through a proxied record. The origin answers
only what arrives with the certificate your zone presents to origins (zone-level
authenticated origin pulls, with a certificate of your own rather than Cloudflare's shared
one). Every origin trusts the CA of every client certificate the zone holds. If the zone
holds none, ocel mints a CA and a client certificate it signs, both good for ten years,
uploads the client certificate, has the origin trust the CA, then turns zone-level pulls on.
The client certificate carries its CA in its CA Issuers access (a `data:` URI), which is how
a later deploy reads the CA back from the zone. Two deploys that find the zone holding none
at once each upload one, and the one that uploaded second deletes its own, so the zone keeps
one. Past that, ocel never replaces or deletes a zone's client certificate: it is shared by
every origin the zone forwards to. A load balancer on AWS or Google Cloud refuses the
certificate once it or its CA lapses; the origins on a VPS box accept it past its expiry,
except behind your own Traefik. A zone that already presents Cloudflare's shared
certificate (global pulls on, or zone-level pulls on with no certificate of the zone's own)
is refused, since another origin in it may trust only that one: upload a certificate of
your own first.

To rotate the certificate, or retire a leaked key, upload the new one to the zone
(**SSL/TLS > Origin Server > Authenticated Origin Pulls**). ocel must be able to read the CA
it chains to: upload a self-signed certificate, or one that names its CA's certificate as a
`data:application/pkix-cert;base64,` URI in its CA Issuers access, as ocel's own does. A
load balancer on AWS trusts only a CA, so behind one only the second kind works; a deploy
refuses a zone holding a certificate whose CA ocel cannot read. Cloudflare presents the
certificate uploaded last at once, so until the next step origins refuse it. Deploy one
project on each VPS box, on each Google Cloud tier and on each AWS tier with container apps
the zone forwards to: each origin then trusts both. Delete the old certificate from the
zone, then deploy every project with a hostname in the zone once more: an origin stops
trusting the old CA for a hostname once that hostname's own project deploys, since another
zone may still present it.

Cloudflare reaches the origin over plain http when the visitor used it, and the origin
answers that with a redirect to https without forwarding it, so ocel changes neither Always
Use HTTPS nor any redirect rule in your zone.

A promote purges what Cloudflare cached for the hostnames it moved to the new release. Unless
the edge sets `tunnel`, the zone's SSL mode must be Full (strict). The token needs Zone Read,
Zone Settings Read, DNS Edit, SSL and Certificates Edit and Cache Purge on the zone, and
Account Settings Read on the account; with `tunnel`, it also needs Cloudflare Tunnel Edit on
the account.

On a VPS box, `"edge": { "cloudflare": { "tunnel": true } }` reaches the box through a
Cloudflare Tunnel instead of at its address, with no certificates and no SSL mode to set;
see [through a Cloudflare Tunnel](/docs/providers/vps#through-a-cloudflare-tunnel). Other
providers refuse `tunnel`.

Hostname records go into the origin provider's own DNS unless you say otherwise. Write
them into Cloudflare instead:

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": "aws",
  "edge": "cloudflare",
  "dns": "cloudflare",
  "apps": [{ "name": "web", "path": "." }]
}
```

Dev mode starts the resources the app declares on your machine, linked or not, and reads its values from `.env`, or from the env source the config names for dev, with `.env.local` on top.

## Container apps on AWS

On [AWS](/docs/providers/aws), Cloudflare runs a worker in front of serverless apps and no
worker in front of container apps, and one project can have both. A container app's
hostname gets a proxied record pointing at a public load balancer, one per tier, which the
first such app raises (about $16 a month plus traffic). The load balancer admits only
Cloudflare's addresses and checks the client certificate your zone presents, as a VPS box
does. It redirects plain http to https with a 301, since an AWS load balancer cannot send a 308. Each hostname gets an ACM certificate, validated through the DNS writer. A preview
of a container app gets a proxied record of its own and a route that runs no worker. The
record wins over the wildcard record and the route over the wildcard route. Removing the
preview removes both.

The load balancer holds at most 25 certificates besides its default, one per production
hostname and one per preview wildcard, at most 100 rules, one per hostname and live preview,
and a trust store of at most 25 CAs, one per zone that forwards to it. These limits cover
every project in the tier, and AWS raises each on request: a deploy that reaches one is
refused naming the Service Quotas entry to raise (Elastic Load Balancing, L-9365A611 for
certificates, L-7EED9B64 for rules, L-43FE5A42 for CAs). It reaches at most 100 target
groups, which AWS does not raise: one per release of a container app, kept ones included.
The trust store holds only the CAs a hostname behind it still trusts: removing a hostname
drops a CA no other hostname trusts. A certificate ocel did not request for the hostname,
such as one it found in ACM and reused or the one `ocel domain use --preview` wildcard every
project's previews share, stays on the load balancer once the hostname is removed, since
another project's hostname may answer with it.

Middleware, the edge runtime and edge caching need the worker, so a container app behind
Cloudflare is served streaming alone. A deploy of one that needs more is refused unless
`allowDegraded` names the need.

## Previews behind Cloudflare

A preview wildcard is forwarded to the origin through one proxied `*.<base>` record, and
the origin answers each preview under it only to Cloudflare. Cloudflare's Universal SSL
covers the zone apex and the names one label below it, so a preview domain at a zone apex
(`*.acme-previews.com`, with `acme-previews.com` a zone of its own) needs nothing more.
Deeper than that (`*.preview.acme.com` in the `acme.com` zone), Cloudflare answers a preview
only with an advanced certificate: ocel orders one and stops, and running the same command
again once Cloudflare has issued it, usually within minutes, finishes. Ordering one needs [Advanced Certificate
Manager](https://developers.cloudflare.com/ssl/edge-certificates/advanced-certificate-manager/),
a paid add-on to the zone; without it ocel refuses the wildcard and says so.
