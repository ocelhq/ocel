```bash
ocel init --provider gcp --option region=europe-west1
```

Name the region (`europe-west1`, never a zone such as `europe-west1-b`), and the project unless `GOOGLE_CLOUD_PROJECT`, `CLOUDSDK_CORE_PROJECT` or your gcloud config already does. `ocel cost scan` reads no credentials and runs no gcloud, so it needs `project` in the config or in one of those two variables:

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import gcpProvider from "ocel/providers/gcp";

export default defineConfig({
  slug: "my-app",
  provider: gcpProvider({ project: "my-project", region: "europe-west1" }),
  apps: [{ name: "web", path: "." }],
});
```

```json tab="JSON" title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "gcp": { "project": "my-project", "region": "europe-west1" }
  },
  "apps": [{ "name": "web", "path": "." }]
}
```

Credentials come from Application Default Credentials:

```bash
gcloud auth application-default login
```

Then:

```bash
ocel deploy
```

In a terminal, a first deploy that finds no Ocel infrastructure in the account offers to run
`ocel bootstrap production`, and carries on once it has. Nothing is asked in a script or in CI,
so run the bootstrap there first:

```bash
ocel bootstrap production
ocel deploy
```

The bootstrap makes only what every deploy needs. The first deploy that needs something more adds
it to the tier with the deploy credential and shows it in its plan: the network a database or kv
store is reached over, and the load balancer of the `alb` edge. `ocel bootstrap status`
lists each of these parts, who added it, which projects use it and what it costs idle, and
`ocel bootstrap production` makes each recorded part again if it was changed or deleted by hand.
`ocel bootstrap production --remove <part>` takes one part down, `cloudflare-origin` included, and
refuses while a project here uses it unless you pass `--force`; the next deploy that needs a part a
deploy adds adds it back. `--force` never takes `private-network` down while a kv store or database
is on it, or `alb` while a hostname is bound to it: remove those first.

A project that declares a topic or task, or whose build revalidates, also gets a Firestore
database of its own in each tier, `<namespace>-<tier>-w-<hash>`, which holds its runs and its Next
tag records. Only that project's apps may write it. The first deploy that needs it makes it, a dry
deploy plans it, and removing the project from the tier deletes it. It has no standing charge, only
the reads, writes and storage its records use.

## Next.js

A serverless Next app runs as Cloud Run services billed per instance, each with 1 vCPU and 2 GiB
of memory. An instance keeps its CPU after it answers, so the work Next runs after the response
(`after()`, refreshing a stale page, writing the cache) finishes rather than stalling until the next request.

The catch is the bill. Cloud Run charges an instance for its whole life, idle time included, and
keeps an idle instance for up to 15 minutes after its last request. At list prices one instance costs
about $0.08 an hour, so traffic that never pauses for 15 minutes keeps one alive all month, about $58,
where billing per request would charge only the seconds spent answering. The per-instance rate is
about a quarter lower and has no per-request fee, so it costs less only for an instance that spends
most of its life, roughly three quarters or more, answering requests. `ocel cost` prices the services
this way.

A Next app on `compute: "container"` runs `next start` in its image with 2 GiB of memory and its
CPU always allocated, so it is billed per instance, and it keeps at least one instance running
unless `instances.min` is 0. It shares the tier's Cloud Storage cache and Firestore tag records
with a serverless Next app, so a revalidated tag reaches every instance, and it refreshes stale
pages in the background. Cloud CDN does not store its pages: ocel marks every response that
names `s-maxage` private, so a revalidated page is never served stale; its hashed static files are
still cached. It may build with `output: "standalone"` and set `adapterPath` in `next.config`: ocel
installs its cache handlers before Next loads. The Next server stops as it starts when the config it
loads names the app's own `cacheHandler`, `cacheHandlers.default` or `cacheHandlers.remote`, whether
`next.config` sets it or `NEXT_CACHE_HANDLER_PATH`, `NEXT_DEFAULT_CACHE_HANDLER_PATH` or
`NEXT_REMOTE_CACHE_HANDLER_PATH` does under `next start`. Other Node processes the app starts are
left alone.

A serverless Next app's static files (the `public` directory, `_next/static` and the prerendered
fallbacks) and its image config are uploaded at deploy to the tier's Cloud Storage bucket, under
the release's storage prefix, and the service reads them from there: its image carries none. A
service account may read only its own app's files. Removing a release removes them with it.

Behind the `alb` edge, a request for a file under one of the build's immutable prefixes, such as
`/_next/static/`, never reaches Cloud Run: the load balancer sends it to a backend bucket over the
tier's bucket, with Cloud CDN caching it, and rewrites the path onto the release's storage prefix.
A promotion or rollback moves that rewrite to the release it serves. Before it moves anything, the
live and the next release are each given the immutable files only the other uploaded, so while the
url map and the service's traffic settle, a page from either release finds its files under either
prefix; the copies are removed with their release. The load balancer's service
agent may list the bucket's object names and read only the static files of releases in it; the
listing is what makes a file missing under an immutable prefix a 404 from the bucket rather than a
403, and never a request to the service.

Each prerendered page renders on its first request after a deploy and is then served from the
cache. With `instances: { min: 0 }`, Cloud Run stops an idle instance after at most 15 minutes, so the
next request starts cold. See [Cloud Run billing settings](https://cloud.google.com/run/docs/configuring/billing-settings).

## Edge

Leave `edge` out of the provider's options and a deployment has no edge in front of it: each service is answered on
the URL Cloud Run gives it, which costs nothing while it serves nothing and binds no
hostname of your own.

A promotion pins all of a service's traffic to the revision its release created, and a
rollback pins it back. The promotion then asks each revision it pinned once, on the app's
health path, so the first visitor does not wait for it to start. It asks the way a visitor
gets in: on the service's own URL with no edge in front, and through the load
balancer on a hostname routed to the service when the `alb` edge serves it. A service a deploy creates answers nobody until its first promotion
opens it, and a first promotion that is taken back closes it again, so a service's default traffic
only ever serves a release the project promoted.

A deployment with no edge in front is answered on its own `run.app` URL, which the deploy
prints, and the service gates itself. A tier's gate, which holds the keys and never
the plain password, is kept in one Secret Manager secret per project and tier, so production and
previews never share one. Every service of the
project in that tier that runs an Ocel runtime in front of the app, a container or a Node, Next or SvelteKit
function, mounts that secret as a volume at version `latest`, whether
[`protection`](/docs/configuration#protection) is on for the tier or not. While it is off, the secret
holds `null`, the runtimes serve every request, and the deploy says the tier answers anyone
who knows its URL. The first deploy of the tier creates the secret, holding the gate if protection is
on and `null` if it is off, and grants the app's service account read access to it before any
service mounts it. Turning protection on
writes the gate to the secret, and the previews already running are gated from then on, without
a deploy and without a new revision.

The container runtime and the Node runtime check every request against the mounted file, which
they read again at most five seconds after they last read it. They answer every request that
carries no credential with the login page, the health check path included, strip the credentials
before the app sees them, and answer 503 while the file is missing, unreadable or takes longer than
two seconds to read. A container's startup probe sends a token that only the service's
configuration holds, and the runtime answers a probe carrying it with the app's status and no body.
A deploy makes the token for any service that has none yet, including one that already exists,
which rolls that service a new revision once; every later deploy keeps the token, so turning
protection on or rotating the password never stops a new instance from starting.
`ocel protection` writes a new secret version, which Cloud Run serves to running instances
without a new revision:
[Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)
says that when it reads a volume, Cloud Run always fetches the secret value from Secret Manager.
The version the new one replaces stays readable, so an instance that resolved `latest` just
before the write still reads it; older versions are destroyed. An app's service account is
shared by every deployment of that app in the tier, and may read the tier's gate secret of the project and
no other: the deploy grants it on that secret alone.

Go, Python and Rust functions run no Ocel runtime in front of the app, so nothing in them checks
the gate. With `protection.<tier>` on, a deployment with one is refused. With it off, the deployment
deploys as before, and Ocel records that the function ignores the gate before its service is
created, and warns if protection was turned on while it deployed them. If protection is turned on
while such a preview is still deployed, every protected preview
deploy says so, and `ocel protection` names each of those functions instead of calling the
tier protected. A change or `ocel protection sync` still writes the gate to every
service that checks it, then exits with an error naming those functions. All of this lasts until
those deployments are destroyed.

A deployment answered by the load balancer is cached, and gated there without
changing that. Each tier's load balancer runs the gate as a Service Extensions plugin
on its forwarding rule, ahead of the URL map and Cloud CDN, so it sees every request,
including one a cache would answer, and a response the gate admitted is cached exactly as an
ungated one would be. The deploy never rewrites an app's `Cache-Control` for a gate. The plugin
admits a request carrying the tier's password, a bypass secret or a session, takes those
credentials off before the request goes on, and answers everyone else with the login page.
The login is answered by the plugin too, from the password sent as HTTP Basic credentials,
so the password never reaches the service. Every preview response carries `X-Robots-Tag: noindex`, set on the
preview backends and on the assets bucket, and so does everything the gate itself answers.

The plugin and its config share the 5 MiB Google allows a plugin, and the config holds each
gated project's keys and hostnames, so it grows with the hostnames a gated project
has live. A deploy that would pass the limit is refused, naming it. The plugin is kept as a
generic artifact in an Artifact Registry repository of its own in your project, and the
config is readable by anyone who may read the load balancer's plugin and is kept sealed in
ocel's state.

A new gate, and a new hostname of a gated project, take a few minutes to reach
every location that serves requests, and during them a request may still pass ungated. A
deploy that adds one therefore leaves the hostname unrouted, publishes the gate, and
asks the hostname through the load balancer until the gate's own refusal answers five times
in a row, for up to about five minutes, before it routes the hostname. If the gate never
answers, the deploy fails and the hostname stays unrouted. A project that gates an
already-routed preview waits the same way, and that preview is open until the wait ends.
Changing or revoking a password or secret takes the same few minutes to apply, and
`ocel protection` streams the rollout while it waits.

The deploy that adds the load balancer attaches the plugin with an empty gate set that admits
everything, and a plugin that crashes refuses requests rather than passing them. That deploy checks
the Service Extensions API (`networkservices.googleapis.com`) is on, and the deploy credential
holds `roles/networkservices.admin`. A load balancer only Cloudflare
reaches attaches no plugin: the worker in front of it runs the gate.

A service behind the load balancer takes traffic from the load balancer alone, so its
`run.app` URL does not answer: there is no way round the gate to it.

A hostname on Google Cloud costs a load balancer. Name the `alb` edge and the first deploy
behind it adds one global external Application Load Balancer per tier — one address, one
certificate map, one URL map, Cloud CDN on every backend — and every project in that tier
is answered by it. It is the only thing ocel provisions on Google Cloud that bills while
it serves no traffic: about $18 a month per tier for the forwarding rule, plus
Premium-tier egress. The deploy plan says so before it provisions anything, and the destroy of
the last project behind it, or the deploy that moves that project to another edge, takes it
down again. One that still has a hostname bound stays until the hostname is released.
Binding a preview wildcard with `ocel domain use --preview` uses the same load balancer: it adds
it if no deploy has, `ocel bootstrap status` lists the wildcard among its users, and releasing
the wildcard takes the load balancer down if nothing else is behind it.

The deploy credential adds the load balancer, its gate plugin and the Artifact Registry
repository the plugin is kept in under the roles that bind hostnames, and creates and deletes
that repository through the parts role [below](#what-to-grant).

The bootstrap also keeps one custom role,
`projects/<project>/roles/<namespace with _ for ->_cdn_purge`, holding only
`compute.urlMaps.invalidateCache`: the serverless Next apps behind the load balancer are granted it to clear
revalidated pages from Cloud CDN, and nothing else. It costs nothing, and a bootstrap never
deletes it, because Google holds a deleted custom role's id for up to 44 days. A role deleted by
hand is undeleted within Google's first 7 days, and one whose permissions drifted is put back.

Cloud CDN passes the `Cache-Tag` response header through to clients, so the tag names a Next app
stamps on its pages, including the release, are visible to visitors: never put a user or tenant id
in a tag.

A Next page with a `revalidate` time is refreshed by Cloud CDN, not by the app. The app answers
with `s-maxage` and `stale-while-revalidate` taken from the route's revalidate and expire times,
and treats a stale entry in its own cache as a miss. Cloud CDN keeps the page for `s-maxage`
seconds, then asks the app for a fresh one, sending one request to the app however many visitors
ask for that page at once. Google's documentation disagrees on what visitors get during that
request: [Serving stale content](https://cloud.google.com/cdn/docs/serving-stale-content) serves
the old page for up to the `stale-while-revalidate` time while the refresh runs in the background,
and [Caching overview](https://cloud.google.com/cdn/docs/caching) says a response with `s-maxage` is
never served stale. In the second case the refresh is synchronous: the first visitor after
`s-maxage` waits for the app to render the page. Either way, no visitor gets a page older than the
route's expire time. A response without `stale-while-revalidate` is never served stale.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
  provider: gcpProvider({ project: "my-project", region: "europe-west1", edge: alb() }),
  apps: [{ name: "web", path: "." }],
```


Certificates are issued by Certificate Manager against a DNS authorization: ocel hands you
the CNAME to write and renews through it. Every service behind the load balancer takes
ingress `internal-and-cloud-load-balancing`, so its `run.app` URL stops answering from the
internet.

Run `ocel domain use '*.preview.example.com' --preview` and previews are answered by the
same load balancer under one certificate for the wildcard. A preview's promotion writes an
exact host rule for its hostname onto a serverless network endpoint group that names that
preview's own Cloud Run service, so a hostname reaches the one service it was routed to and
nothing else, and a hostname no preview serves is answered 404 by the load balancer. The
rule comes down with the preview. Each preview hostname is a backend service of its own, so
the project's backend service quota bounds how many previews a tier answers at once, and a
promotion that would pass it is refused before anything is provisioned. Each
deployment of a preview is also answered on a hostname of its own, routed to the Cloud Run
revision tag that deploy created, so an older deployment keeps serving what it shipped after
the alias moves on, until `ocel preview prune` or `ocel preview rm` drops it. A project that
declares its own `domains.preview` wildcard is served the same way: the wildcard's
certificate is entered on the preview tier's load balancer, and each of the project's
previews is an exact host rule under it.

[`cloudflare`](/docs/providers/cloudflare) is the edge bought independently of Google.
Name it and a hostname is forwarded through Cloudflare to a load balancer of its own, which
`ocel bootstrap` provisions per tier at the same price as the `alb` one, as the
`cloudflare-origin` part. Only the bootstrap credential may make it, so the first deploy through
Cloudflare records that its project wants it and stops: in a terminal Ocel offers to add it there
and then, and a script or CI is refused with `ocel bootstrap <tier>`, which adds it. That load balancer
refuses any client that does not present the certificate your Cloudflare zone presents to
origins, so a request that skips Cloudflare is turned away. On port 80 it answers every
hostname with a redirect to https and forwards nothing, so a visitor who opens `http://`
lands on https through Cloudflare, which reaches the load balancer over plain http whenever
the visitor did. That port 80 listener is a second forwarding rule, which costs nothing more
while the project holds five or fewer. The wildcard `ocel domain use
--preview` names is forwarded the same way, to a host rule on that load balancer; see
[previews behind Cloudflare](/docs/providers/cloudflare#previews-behind-cloudflare).
That is how container apps are served. A serverless app is not forwarded: Cloudflare runs a
worker in front of it and reaches each deployment on a hostname under an `originDomain` you
name, as
[serverless apps on Google Cloud](/docs/providers/cloudflare#serverless-apps-on-google-cloud)
describes.

```ts tab="TypeScript" tab-group="config" title="ocel.config.ts"
import { defineConfig } from "ocel/config";
import { cloudflareDns } from "ocel/dns";

  slug: "my-app",
```


## Buckets

`bucket("uploads")` is one Cloud Storage bucket per environment, in the bootstrap's region, under
uniform bucket-level access with public access prevention enforced. Only the service accounts of the
apps that bind it may read and write its objects. Each environment of an app runs as an account of
its own, so `web` running in one preview reaches no other preview's buckets. See [Buckets](/docs/sdk/bucket#on-google-cloud) for how
signed urls and uploads work there.

## Postgres

`postgres("orders")` is one Cloud SQL for PostgreSQL instance per environment, sized by the
environment's tier. In production it runs the Enterprise edition's dedicated-core `db-custom-1-3840`
(1 vCPU, 3.75 GB; about $98.60 a month in `us-central1` at the high-availability rate) as a regional
instance with a standby in a second zone, 10 GB of SSD that grows as it fills (about $0.34 per GB a
month), daily backups with point-in-time recovery, and deletion protection, which ocel lifts only
when it removes the database. A preview runs the shared-core `db-f1-micro` (about $7.70 a month) in
one zone, with 10 GB of SSD (about $0.17 per GB a month) and daily backups; Google's SLA does not
cover shared-core instances. An instance bills by the hour whether it serves anything or not, and a
deploy patches an instance that has drifted from its tier's size back to it, which restarts the
instance. Each app's Cloud Run services together open at most what the instance's connections
allow: 100 in production and 25 in a preview, less 3 Cloud SQL reserves, at up to 10 per instance.
`version` `"14"` to `"17"` picks the major version, `"17"` when you leave it out; a major version is
not changed in place, so a deploy asking for another one is refused.

The instance has no public address. It is reached at a private address on the tier's
[private network](#private-network), made for it by a Private Service Connect endpoint that
bills about $7.30 a month of its own, and refuses any connection that is not encrypted. Apps connect as the `ocel` user to the `ocel` database with a
password ocel generates, keeps sealed under the tier key, and hands each app in its binding.

Creating an instance takes several minutes. `ocel destroy`, or dropping the database from the
code, deletes the instance and its data; a database created again afterwards is
a new, empty instance.

## KV stores

`kv("cache")` runs as one Memorystore for Valkey instance per store: cluster mode off, one
node, plus one replica in another zone in production and none in a preview. The node is the smallest whose keyspace holds the store's `memory`, from
`custom-pico` (1.08 GB, about $22 a month in `us-central1`) up to `highmem-xlarge`, and
`maxmemory` is set to `memory`. A store above 32gb is refused when the deploy is planned. `eviction` is sent as declared, and as
`noeviction` when you leave it out, since Memorystore's own default is `volatile-lru`.
`version` `"8"` runs Valkey 8.0 and `"9"` runs 9.1.

Writes go to an append-only file synced every second, so a crash loses about the last second
of writes. A node bills by the hour whether it serves anything or not, and the append-only
file adds a charge for the node's capacity. A production store's replica bills as a second node
with its own append-only file, and Memorystore promotes it if the primary or its zone fails. A
preview store has no replica, so it loses its data if its zone goes down, and a failed node takes
minutes to repair.

Apps authenticate with the token Memorystore generates for the default user, which ocel
reads back on every deploy, and reach the store over TLS under the instance's own certificate
authority, which every SDK's client trusts from the binding.

A store is reached over the tier's [private network](#private-network). `ocel destroy` deletes
the instance and its data.

## Private network

KV stores and databases are reached over a network of the tier's own, which the first deploy
declaring one adds as the tier's `private-network` part. Switch its services on first:

```bash
gcloud services enable compute.googleapis.com memorystore.googleapis.com sqladmin.googleapis.com \
  networkconnectivity.googleapis.com serviceconsumermanagement.googleapis.com \
  servicenetworking.googleapis.com --project my-project
```

That is one VPC network with one subnetwork, `10.240.0.0/20`, in the bootstrap's region, and
the service connection policies Memorystore and Cloud SQL connect each instance through. None of
it bills. A deploy that finds a service switched off is refused, naming the command that switches
it on. The bootstrap grants the Cloud Run service agent `roles/compute.networkUser` on the project,
so Cloud Run services and functions bound to a store or database reach private addresses over
that subnetwork through direct VPC egress; the rest of their traffic leaves as before.

**Removing it.** `ocel bootstrap destroy` takes the network down, and is refused while any store
or database is still on it, naming them. The bootstrap credential needs
`roles/compute.networkAdmin` and `roles/cloudsql.viewer` for that.

## Topics, tasks and workers

Each topic and task is a Pub/Sub topic, and each of its consumers gets a push subscription of
its own. Pub/Sub redelivers a message until its run settles, and a run that spends its attempts
settles failed, a dead letter to list or redrive. A task with a `cron` is a Cloud Scheduler job publishing to its
topic. Runs are kept in the project's own Firestore database, which no other project's apps may
read or write, and a delayed send or trigger waits in the tier's Cloud Tasks queue until it is due.

Each worker runs as a second Cloud Run service from its app's image, scaled from zero, reached
by Pub/Sub alone: its ingress is internal, and only the tier's push account may invoke it. A run
gets at most 600 seconds, the longest a push subscription waits for an answer.

The bootstrap makes the tier's delay queue, `<namespace>-<tier>-delays`, and the push account
Pub/Sub signs each push as, so it wants Cloud Tasks and Pub/Sub on. The first deploy declaring a
topic or task makes the project's own database of runs.

None of it bills while idle. A Next app that declares neither uses no queue. `ocel bootstrap
destroy` deletes every project's databases and purges the queue, keeping it, since Cloud Tasks will
not make a queue under a deleted queue's name for 7 days. It needs `roles/cloudtasks.admin` in the
bootstrap credential.

What differs from `ocel dev`: lanes are recorded but not weighted, a batch consumer receives
batches of one, a task's own `concurrency` is not enforced (its worker's is), and a batch trigger
is not atomic. A deploy that changes a topic's `ordered` is refused while any of its consumers is
kept, since Pub/Sub cannot change a subscription's ordering: rename the consumers to change it.

A deploy also keeps the app's access to the tier's delay queue, and Google cannot narrow that
grant by condition, so you give the deploy credential the role on exactly that queue, once per
tier:

```bash
gcloud tasks queues add-iam-policy-binding ocel-production-delays \
  --location=europe-west1 --project=my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/cloudtasks.queueAdmin
```

A project with a preview tier needs the same grant for `ocel-preview-delays`. A deploy that
lacks it is refused, naming it.

## Realtime

Each environment's realtime resources share one Cloud Run service running the Ocel gateway,
which runs as a service account of the tier's own that may read the tier's realtime keys
and no other secret. See [Realtime](/docs/sdk/realtime#on-google-cloud) for how sockets,
publishes, keys, upgrades and cost work there.

Each environment's gateway runs up to 10 instances of 950 sockets each. Cloud Run cannot route a
publish to one instance, so each instance hears every publish through its own subscription to the
environment's Pub/Sub topic: it makes the subscription when it starts and deletes it when it stops,
and a subscription left by an instance that was killed expires a day after its last pull. Sockets
on an older revision keep receiving while it drains. The tier's realtime account may publish on and
subscribe to its environment's topic, and holds the `<namespace>_realtime_subscriptions` role on the
project to make, pull and delete subscriptions; Pub/Sub honours no IAM condition, so that role
reaches every subscription in the project. A tier bootstrapped before this needs `ocel bootstrap`
again.

## Logs

Cloud Run services and workers log to Cloud Logging in your project, which keeps them for as
long as the project's `_Default` log bucket does: 30 days unless you've changed it. Read them
with [`ocel logs`](/docs/cli/logs), which also lists the Cloud Logging quotas a read or a tail
shares.

## What to grant

Turn the services on once:

```bash
gcloud services enable firestore.googleapis.com storage.googleapis.com \
  cloudkms.googleapis.com secretmanager.googleapis.com artifactregistry.googleapis.com \
  iam.googleapis.com run.googleapis.com cloudscheduler.googleapis.com \
  iamcredentials.googleapis.com pubsub.googleapis.com cloudtasks.googleapis.com --project my-project
```

Apps sign their buckets' urls through `iamcredentials.googleapis.com`.

A deploy needs `roles/datastore.user`, `roles/storage.objectAdmin`,
`roles/cloudkms.cryptoKeyEncrypterDecrypter`, `roles/secretmanager.secretAccessor`,
`roles/artifactregistry.writer`, `roles/iam.serviceAccountUser`, `roles/run.admin`,
`roles/memorystore.admin`, `roles/pubsub.admin` and `roles/cloudscheduler.admin`, and the
custom roles `ocel bootstrap` keeps for it.

The custom role lets a deploy create the service accounts its apps run as and set who may act as
them, and nothing else: it holds `iam.serviceAccounts.create`, `.get`, `.getIamPolicy` and
`.setIamPolicy`, and no permission to delete, disable, update or key an account.
`ocel bootstrap` creates it as `projects/<project>/roles/<namespace with _ for ->_app_accounts`, so you
grant it to the deploy credential after the first bootstrap:

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=projects/my-project/roles/ocel_app_accounts
```

An app that reaches topics, tasks or workers may act as its own account, and so may Cloud Tasks,
because a delayed message is published as the app that sent it.

The first deploy that needs a part of the bootstrap adds it with one more custom role the
bootstrap keeps. `<namespace with _ for ->_parts` creates the tier's network, subnetwork and
service connection policies, uses that network and subnetwork as the policies need, creates the
repository the load balancer's gate plugin is kept in, and reads whether a service is on. Compute
Engine, Network Connectivity, Artifact Registry and Service Usage name no resource attribute a
condition could hold those by, so it is granted unconditioned; it deletes nothing but that
repository, which the last project behind the load balancer takes down with it.

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=projects/my-project/roles/ocel_parts --condition=None
```

`<namespace with _ for ->_project_records` makes the Firestore databases each project keeps its
values, runs and tag records in, with their indexes and time to live, and the key its values are
sealed under. It can also delete the database of a project's runs when the project is removed. It is
granted on a condition naming the `<namespace>-<tier>-v-` and `-w-` database prefixes and the
`<tier>-p-` keys, so it reaches no other database or key.

`ocel permissions deploy` prints each grant with its condition for your namespace.

A bootstrap never deletes the role, because Google holds a deleted custom role's id for up to 44
days and nothing could make it again in that time. A role deleted by hand is undeleted within
Google's first 7 days, and one whose permissions drifted is put back.

Each app runs as a service account of its own, which a deploy creates the first time the app
ships to a tier and grants only what the app's runtime reads: read access to its project's values
database and decrypt on its project's key (and the same for any project its values reference); for
a Next app with an incremental cache, or an app that reaches topics, tasks or workers, write access
to its project's own database of runs and tag records and no other; for an app that reaches topics,
tasks or workers, the delay queue and its topics; and for a serverless Next app the delay queue. Granting those takes `roles/resourcemanager.projectIamAdmin`, and
a deploy holds it under a condition that lets it grant and revoke the four roles an app needs and
the custom role that clears Cloud CDN, and no others:

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/resourcemanager.projectIamAdmin \
  --condition="title=ocel app grants,expression=api.getAttribute('iam.googleapis.com/modifiedGrantsByRole', []).hasOnly(['roles/datastore.viewer', 'roles/datastore.user', 'roles/cloudkms.cryptoKeyDecrypter', 'roles/storage.objectUser', 'roles/storage.objectViewer', 'projects/my-project/roles/ocel_cdn_purge'])"
```

A serverless app behind the load balancer that revalidates, a Next app or a Node app whose build declares the `revalidation` need, is also granted that role, which holds `compute.urlMaps.invalidateCache` and nothing else, so `revalidateTag` clears the tag from Cloud CDN. Google cannot scope the permission to one URL map, so the grant covers every URL map of the project.

Google limits how many service accounts a project may hold, and every app takes one per tier:
a deploy that reaches the limit is refused, naming the quota. A deploy never deletes an account:
`ocel bootstrap <tier>` deletes the accounts of apps no environment of that tier runs, and the
delay account an earlier version of ocel created for a tier bootstrapped before.

A deploy also keeps the realtime secrets of its namespace, and nothing else: grant
`roles/secretmanager.editor` under a condition naming them. Every realtime secret's id
starts with the namespace and `_realtime-`, and IAM names a secret by the project's number.

```bash
NUMBER=$(gcloud projects describe my-project --format='value(projectNumber)')
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/secretmanager.editor \
  --condition="title=ocel realtime secrets,expression=resource.name.startsWith('projects/$NUMBER/secrets/ocel_realtime-')"
```

A deploy also keeps the gate secrets of its namespace, and sets who may read each: it
grants an app's service account `roles/secretmanager.secretAccessor` on its project's gate secret
alone. Grant `roles/secretmanager.admin` under a condition naming ids that start with the
namespace and `_gate-`; it reaches no other secret.

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/secretmanager.admin \
  --condition="title=ocel gate secrets,expression=resource.name.startsWith('projects/$NUMBER/secrets/ocel_gate-')"
```

A prune or a destroy untags the images no Cloud Run revision runs any more, and the
repository deletes an untagged image a week later. A deploy that finds its image already
pushed tags it again if a prune untagged it since. Artifact Registry takes no condition on
an image's name, so grant `roles/artifactregistry.repoAdmin` on the two repositories the
bootstrap makes, one per tier, and nowhere else:

```bash
for tier in preview production; do
  gcloud artifacts repositories add-iam-policy-binding ocel-my-project-$tier \
    --location=europe-west1 --project=my-project \
    --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
    --role=roles/artifactregistry.repoAdmin
done
```

A deploy also creates and deletes the buckets an app declares, and lets the apps that bind them use
their objects, which is a binding on each bucket and not a project role. The buckets are named for
the namespace and two dashes, which no namespace contains: grant `roles/storage.admin` under a
condition naming them.

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/storage.admin \
  --condition="title=ocel buckets,expression=resource.name.startsWith('projects/_/buckets/ocel--')"
```

Once a tier has its [private network](#private-network), a deploy also creates, changes and
deletes the Cloud SQL instances its databases run on, named the same way: grant
`roles/cloudsql.admin` under a condition naming them. Cloud SQL names an instance by the
project's id:

```bash
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=roles/cloudsql.admin \
  --condition="title=ocel databases,expression=resource.name.startsWith('projects/my-project/instances/ocel--')"
```

Cloud Storage, Cloud SQL and Secret Manager check creating a bucket, an instance or a secret,
listing instances and reading Cloud SQL's operations against the project, where no name
condition admits them, so a deploy also needs a custom role holding those permissions alone.
It may create a secret under any name, and writes and deletes only its own; it reads
the settings of every instance in the project, and changes none of them:

```bash
gcloud iam roles create ocelDeployCreates --project my-project \
  --permissions=storage.buckets.create,cloudsql.instances.create,cloudsql.instances.list,cloudsql.instances.get,secretmanager.secrets.create
gcloud projects add-iam-policy-binding my-project \
  --member=serviceAccount:deploy@my-project.iam.gserviceaccount.com \
  --role=projects/my-project/roles/ocelDeployCreates --condition=None
```

A bootstrap needs those, with `roles/secretmanager.admin` unconditioned in place of the
realtime grant, plus `roles/datastore.owner`, `roles/storage.admin`,
`roles/cloudkms.admin`, `roles/artifactregistry.admin`,
`roles/iam.serviceAccountAdmin`, `roles/iam.roleAdmin`, `roles/resourcemanager.projectIamAdmin`,
`roles/cloudscheduler.admin`, and, to take down the parts deploys added, `roles/compute.networkAdmin`,
`roles/cloudsql.viewer` and `roles/cloudtasks.admin`. Anything missing is named back to you before
anything is created.
