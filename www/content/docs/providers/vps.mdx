---
title: VPS
description: Deploy to any Linux box.
---

```bash
ocel init --provider vps
```

Name the machine ocel deploys onto — a `Host` alias from your `ssh_config`, or the
destination spelled out:

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "vps": { "ssh": { "host": "${DEPLOY_HOST}", "user": "deploy" } }
  },
  "apps": [{ "name": "web", "path": ".", "compute": "container" }]
}
```

Then:

```bash
ocel bootstrap production
ocel deploy
```

Bootstrap creates the `ocel-deploy` login every later deploy acts as.

## Bootstrap

`ocel bootstrap <tier>` prepares the machine once per tier (`production`, `preview`).
Running it again changes only what has drifted, and `ocel destroy` removes it all.
If something else already listens on port 80 or 443, bootstrap names it and stops before it
changes anything: stop it, or run ocel [behind it](#behind-your-own-proxy).

| What | Why |
| --- | --- |
| `ocel-deploy` login, `/var/lib/ocel/.ssh/authorized_keys` | Every deploy logs in as this account. The keys are copied from the login you bootstrap with, or taken from `deployKey`. |
| `/etc/ocel/<tier>/seal.key`, `/usr/local/lib/ocel/seal`, a sudoers line | Secret values are sealed to a key that never leaves the machine. `ocel-deploy` may run the seal helper as root and nothing else. Lose the key and the values can't be opened again. |
| `/var/lib/ocel/<tier>/keyvalues`, `/usr/local/lib/ocel/keyvalues` | What is deployed, per tier. |
| `/var/lib/ocel/releases`, `/usr/local/lib/ocel/releases` | The release window: which images a rollback can still reach. Older images are swept. |
| Docker | Installed once with Docker's install script, pinned by sha256. A Docker 28.0 or later that `docker.service` already runs is used as it is. Either way, upgrading it is yours. Bootstrap refuses a Docker older than 28.0, the snap package, a rootless Docker, and a masked `docker.service`, and says what to change. Docker stays after `ocel destroy`, and so do its containers. |
| `/var/lib/ocel/proxy.json` | Which proxy fronts the box, and which project and tier set it. A deploy whose `proxy` option disagrees is refused. |
| `ocel-proxy` container, `/var/lib/ocel/proxy/caddy.json` | Caddy on ports 80 and 443. It gets a certificate for a hostname the box serves the first time a client connects to it. Left out [behind your own proxy](#behind-your-own-proxy). |
| `ocel-switchboard` container, the `ocel` network, `/usr/local/lib/ocel/switchboard`, `/run/ocel-switchboard`, `/run/ocel-front` | Routes each hostname to the app that serves it, and tells the proxy which hostnames it may get a certificate for. Behind your own proxy it is published on `127.0.0.1:8480`, or joins the docker network your proxy is on. If a prune removes it, or its `ocel` network, while it is stopped, the next deploy recreates both, and `ocel doctor` says when. |
| `/var/lib/ocel/routing/table.json` | The routing table: which project claims each hostname, where each app is served from, and the certificates you pin. Deploys rewrite it and the proxy's config together. |
| `/var/lib/ocel/proxy/data` | Certificates, their keys and the ACME account key. A certificate for a hostname the box stopped serving stays until it has been expired for 14 days, when Caddy removes it. If Caddy still has that certificate in memory when it removes it, the next TLS connection for the hostname can get a new certificate without the switchboard's confirmation. A restart of `ocel-proxy` clears that memory. Left out behind your own proxy. |
| `/etc/ocel/certs` | Certificates you pin yourself. The proxy serves a pinned certificate for every hostname it covers, ahead of any certificate it got itself, and gets none of its own for those hostnames. Left out behind your own proxy. `ocel destroy` removes the directory only if it is empty. |
| `/etc/sudoers.d/ocel-caddy-reload` | Only [behind your Caddy](#behind-your-caddy) when it runs as `caddy.service`: lets `ocel-deploy` run `systemctl reload caddy.service` and nothing else. |
| `ocel-live.socket`, `ocel-live.service` | Serve each app container its secret values over a unix socket. |
| `ocel-envsourcesync@<tier>.service` | Once a minute, copies each env source a deploy registered into the tier's values. It runs as root, and may write `/var/lib/ocel/<tier>/keyvalues` and nothing else. |
| `ocel-backups.timer` | Dumps every resource once a day, and at boot if a day was missed. |

## Behind Cloudflare

Name the `cloudflare` edge and each hostname is forwarded to the box through Cloudflare: ocel
writes a proxied record pointing at the box, and a deploy flips which release answers it on
the box, with no DNS change. The proxy on the box answers that hostname only to a client
presenting the certificate your Cloudflare zone presents to origins, so a request that
skips Cloudflare is refused: on port 443 without that certificate, and on port 80 always.
It answers with a certificate from Cloudflare's origin CA, which ocel issues for the hostname and renews half way through its year, rather than one ordered
from a public CA through Cloudflare. Set the zone's SSL mode to Full (strict). Previews are
forwarded the same way, on a project's own `domains.preview` wildcard or the one
`ocel domain use --preview` names; see [previews behind Cloudflare](/docs/providers/cloudflare#previews-behind-cloudflare).

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": { "vps": { "ssh": "my-box" } },
  "edge": "cloudflare",
  "apps": [{ "name": "web", "path": ".", "domains": { "production": "shop.example.com" } }]
}
```

`ocel doctor` checks a hostname Cloudflare forwards by requesting it through Cloudflare and
checking this box answers, since it resolves to Cloudflare rather than to the box.

Behind [your own proxy](#behind-your-own-proxy), ocel cannot make it refuse a request that
skips Cloudflare. Configure it to require a client certificate for each hostname Cloudflare
forwards, trusting only the certificates listed for that hostname under `shields` in
`/var/lib/ocel/routing/table.json`, and serve it with the origin certificate listed beside
them. On port 80 a request carries no client certificate, so refuse those hostnames there
or redirect them to https. A deploy refuses to forward a hostname your proxy answers to a
client with no certificate or forwards over plain http, and `ocel doctor` fails it.

[Behind your Caddy](#behind-your-caddy), the site block ocel places requires no client
certificate yet, so a deploy refuses to forward any hostname through Cloudflare there.

## Behind your own proxy

If the machine already runs a proxy on ports 80 and 443, ocel can sit behind it instead of
running its own:

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "vps": { "ssh": "prod", "proxy": "manual" }
  },
  "apps": [{ "name": "web", "path": ".", "compute": "container" }]
}
```

Bootstrap then runs no `ocel-proxy`. The switchboard, which routes each hostname to its
app, listens on `127.0.0.1:8480`. Name another port with
`"proxy": { "manual": { "port": 9000 } }`. Ocel never writes to your proxy. You route each
hostname yourself, and `ocel domain add` prints the route it needs:

```
Route shop.example.com → http://127.0.0.1:8480 (keep Host, set X-Forwarded-Proto)
```

A catch-all works too. In nginx:

```nginx
client_max_body_size 0;

location / {
    proxy_pass http://127.0.0.1:8480;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

A proxy running in a container can't reach the host's loopback. Name the docker network it
runs on, and the switchboard joins it:

```json
"proxy": { "manual": { "network": "web" } }
```

Your proxy then forwards to `http://ocel-switchboard:8080`. The switchboard stays on that network
when your proxy is recreated, by `docker compose up` after its definition changes or by the tool
that runs it, so nothing has to be reconnected. Bootstrap refuses a network the machine doesn't
have, so start your proxy, or `docker network create web`, first. The switchboard is still
published on the loopback port as well.

After printing the route, `ocel domain add` waits until the box proves it: a request to
`127.0.0.1:443` for the hostname must come back from ocel, with a certificate that covers the
name, `X-Forwarded-Proto: https`, and the hostname in `Host` and in `X-Forwarded-Host` if your
proxy sets it. A preview base asks for `*.<base>` and is proved on `ocel-edge-probe.<base>`.

The switchboard keeps `X-Forwarded-Proto` and `X-Forwarded-Host` from your proxy, because apps
build their URLs from them. It hears them only from the `ocel` network, which the loopback
port arrives on, and from the network `network` names, and never from your apps' own networks.
Every container on that network can set them, so name one only your proxy and what you trust
sit on. It never takes `X-Forwarded-For` from
your proxy: every process on the machine reaches the same port, so any of them could claim to
be any client. Apps see your proxy's address as the client. No other `X-Forwarded-*` header,
no `Forwarded`, `X-Real-Ip` or `True-Client-Ip` header, and none of these spelled with `_` for
`-`, reaches an app from anyone.

Your proxy manages the certificates, so `certificates` and `proxy` can't be set together. One
proxy fronts a box. Every project on it must name the same `proxy`, and a deploy that
doesn't is refused with the value to write. Moving a box from one proxy to another isn't
supported yet.

| | Ocel's own proxy | `manual` | `traefik` | `caddy` |
| --- | --- | --- | --- | --- |
| Listens on ports 80 and 443 | ocel | you | your Traefik | your Caddy |
| Routes each hostname to ocel | ocel | you | ocel writes the routers | ocel writes `ocel.caddy` |
| Issues and renews certificates | ocel, over http-01 | your proxy | your Traefik, through `resolver` | your Caddy |
| Serves the certificates you pin | yes | no, configure them in your proxy | no, configure them in your Traefik | no, configure them in your Caddy |
| Forgets a certificate when a hostname goes | yes | no, your proxy keeps it | no, Traefik keeps it | yes, 14 days after it expires |
| Reports a Let's Encrypt rate limit | yes | no | no | no |
| Answers every preview hostname under a base | yes | once you route `*.<base>` | each claimed preview hostname | each preview hostname as it is claimed |
| Switches releases without dropping requests | yes | yes, the switchboard does it | yes, the switchboard does it | yes, the switchboard does it |

### The `proxy` option

`proxy` names the proxy on ports 80 and 443. Coolify and Dokploy aren't proxies: each runs a
Traefik, or for Coolify a Caddy, and a `preset` fills in how it runs it. A field written beside a
preset overrides it, for a proxy whose configuration you have edited.

```json
"proxy": "manual"
"proxy": { "manual": { "port": 8480, "network": "coolify" } }
"proxy": { "traefik": { "preset": "coolify" } }
"proxy": { "traefik": { "preset": "coolify", "resolver": "le-dns" } }
"proxy": { "traefik": { "directory": "/etc/traefik/dynamic", "resolver": "letsencrypt",
                        "previewResolver": "cloudflare",
                        "entrypoints": { "http": "web", "https": "websecure" },
                        "network": "traefik" } }
"proxy": { "caddy": { "preset": "coolify" } }
"proxy": { "caddy": { "directory": "/etc/caddy/ocel.d", "container": "caddy",
                      "config": "/etc/caddy/Caddyfile", "network": "web" } }
```

| Field | On | What it is | Left out |
| --- | --- | --- | --- |
| `preset` | `traefik`: `coolify`, `dokploy`; `caddy`: `coolify` | The tool that runs the proxy. Fills every other field. | |
| `directory` | `traefik`, `caddy` | The directory the proxy reads ocel's file from: Traefik's `providers.file.directory`, or the directory Caddy imports. | Required, unless `preset` |
| `resolver` | `traefik` | The `certResolver` every hostname's router names. | Required, unless `preset` |
| `previewResolver` | `traefik` | A resolver that can issue `*.<preview base>` over DNS-01. Set, previews share one wildcard certificate. | Each preview hostname gets its own from `resolver` |
| `entrypoints.https` | `traefik` | The entry point ocel's hostname routers attach to. | `websecure` |
| `entrypoints.http` | `traefik` | The entry point ocel's http-to-https redirects attach to. | `web` |
| `container` | `caddy` | The container Caddy runs in. | Caddy runs as `caddy.service` |
| `config` | `caddy` | The config file `caddy reload --config` names inside `container`. | `/etc/caddy/Caddyfile` |
| `network` | all | A docker network the switchboard joins, so the proxy reaches it by name. | |
| `port` | all | The loopback port the switchboard is published on. | `8480` |

A Traefik or Caddy reaches the switchboard over `network` or over `port`, so they can't both be
written. A `port` written beside a preset replaces the `network` it fills. On `manual`, `port` is
always published and `network` is joined as well.

| | `traefik` + `coolify` | `traefik` + `dokploy` | `caddy` + `coolify` |
| --- | --- | --- | --- |
| `directory` | `/data/coolify/proxy/dynamic` | `/etc/dokploy/traefik/dynamic` | `/data/coolify/proxy/caddy/dynamic` |
| `resolver` | `letsencrypt` | `letsencrypt` | |
| `entrypoints` | `http` / `https` | `web` / `websecure` | |
| `network` | `coolify` | `dokploy-network` | `coolify` |
| `container` | | | `coolify-proxy` |
| `config` | | | `/config/caddy/Caddyfile.autosave` |

A preset and the same fields written out are the same proxy, so projects on one box can name it
either way.

### Behind your Traefik

With `"proxy": { "traefik": … }` ocel writes the routers itself, into one file,
`ocel.yml`, in the directory your Traefik's file provider watches. For `shop.example.com` it
writes a router on your https entry point that names `resolver` and forwards to the
switchboard, and one on your http entry point that redirects to https. Your Traefik orders the
certificate the first time it reads the router. Every router is named
`ocel-<hostname with dashes>-<hash>` and carries priority 1000000, so it wins over any router
of yours that Traefik would otherwise sort against it. Ocel writes no catch-all, so a hostname
it hasn't claimed stays with whatever your Traefik does with it now.

The switchboard sits behind your Traefik one of two ways:

- With `network`, the switchboard joins that network and your Traefik forwards to
  `http://ocel-switchboard:8443`. Both presets work this way.
- Without it, the switchboard is published on `127.0.0.1:<port>`. Only a Traefik in the host's
  network namespace can dial that: a host process, or a container with `network_mode: host`.
  Bootstrap refuses a Traefik container that publishes 443 from a docker network, and names
  `network` as the fix.

The directory is often not writable by `ocel-deploy` (Coolify's is `0700` and owned by
another user), so bootstrap mounts it into the switchboard, and the switchboard writes
`ocel.yml` there under a temporary name and renames it into place. Before each write ocel
decodes what it is about to write, and refuses it if it doesn't decode or contains `{{`, which
Traefik reads as a template. One file Traefik can't parse stops it from taking up a change to
any file in that directory, and after a restart it serves none of them. If
someone deletes `ocel.yml` or rewrites it, from a host tool's editor for instance, the next
deploy writes it back.

After each change, ocel waits up to 30 seconds for each hostname the change adds, or whose
router it changes, to answer on `127.0.0.1:443` through the switchboard, whatever certificate
Traefik has for it yet. A hostname the change leaves as it was isn't waited on, so one Traefik
can't route for reasons of its own doesn't hold up the rest. If one doesn't answer, the change is put back and the refusal says what the probe met. When a file of yours
in the directory fails to parse, it names that file. When Coolify has been switched to Caddy,
it says so and gives `{ "caddy": { "preset": "coolify" } }` as the value to write.

**Your routes stay yours.** Before ocel claims a hostname (a binding, a preview, the connector),
it reads the rules of every router your Traefik has: every `.yml`, `.yaml` and `.toml` file in
the directory besides `ocel.yml`, the `traefik.http.routers.<name>.rule` labels of every
running container, and the same labels on swarm services when the box manages a swarm. A
`Host()` equal to the hostname, or a `HostRegexp` that matches it, refuses the claim and names
the router and where it is defined. A `HostRegexp` that matches any hostname at all is a
catch-all and claims nothing. Ocel reads each file the way Traefik does, through the same
template functions. If it can't read a file, a router in it could already route the hostname,
so the claim is refused and the refusal names the file. A template that calls `env`,
`expandenv` or `getHostByName` counts as unreadable too, because it reads what only your
Traefik can see. `ocel doctor` runs the same check, so a router you add after the
bind, which ocel's priority now wins over, is named too. Routers from Traefik's other
providers, such as Consul or Kubernetes, are invisible to ocel, so it can't check them.

**Previews.** Set `previewResolver` to a resolver that can issue a wildcard over DNS-01, and
your Traefik orders one certificate for `*.<preview base>`, through a router on
`ocel-edge-probe.<preview base>` that ocel writes as soon as the preview base is set. Each preview
hostname is then served that certificate. Without `previewResolver`, each preview hostname
gets a certificate of its own from `resolver`, the same as any other hostname.

**Semicolons in the query.** Your Traefik rewrites every `;` in a query to `&` before any router
sees the request, so `?x=1;2` reaches your app as `?x=1&2`. Ocel's routers can't change that,
because it happens on the entry point. Set `http.encodeQuerySemicolons: true` on each entry point
in Traefik's static configuration and the `;` reaches your app encoded as `%3B`, which a query
parser reads back as `x=1;2`.

**Certificate lifetimes.** Your Traefik renews every certificate it stores, for as long as its
`acme.json` holds it, and it deletes none. A certificate for a hostname ocel no longer serves
stays in `acme.json` and keeps being renewed until you remove it there. If Traefik fails to
get a certificate, usually because the hostname's DNS doesn't point at the box yet, it tries
again only the next time its configuration changes, with no backoff. `ocel doctor` flags a
hostname Traefik holds no certificate for: fix the DNS, then restart Traefik or change any route
it serves.

**Coolify and Dokploy.** Both keep running their Traefik as they do now. A prune one of them
runs can remove the switchboard and its `ocel` network while it is stopped; the next deploy
recreates both. `ocel destroy` removes `ocel.yml`, then the switchboard, which takes it off
their network.

A Traefik ocel writes to reaches a switchboard listener that takes every request as https for
the `Host` it asked for, and hears no `X-Forwarded-*` header at all. With `network`, every
other container on that network, which on Coolify and Dokploy means their apps and databases,
can reach that listener too. Without it, the listener sits on the `ocel` network and is
published on `127.0.0.1:<port>`, so every process on the machine and every container on the
`ocel` network can reach it. Any of them can make a plaintext request your apps take as https, for a `Host` it
could send anyway. None of them can choose `X-Forwarded-Host` or `X-Forwarded-For`. This is
the same kind of concession `manual` makes to every process on the machine.

### Behind your Caddy

With `{ "caddy": … }`, ocel writes one file into a directory your Caddy imports, and reloads
your Caddy when the hostnames in it change. Add the import to your Caddyfile once:

```txt title="/etc/caddy/Caddyfile"
import /etc/caddy/ocel.d/*.caddy
```

and name the directory:

```json
"proxy": { "caddy": { "directory": "/etc/caddy/ocel.d" } }
```

Coolify's Caddy already imports `/dynamic/*.caddy`, so `"proxy": { "caddy": { "preset": "coolify" } }`
needs no line of yours.

Ocel writes `ocel.caddy` there and nothing else. It holds one site block over exactly the
hostnames the box serves, the connector's and `ocel-edge-probe.<base>` among them, and never a
bare port:

```txt title="ocel.caddy"
shop.example.com, ocel-edge-probe.preview.example.com, pr-12--web.preview.example.com {
	reverse_proxy ocel-switchboard:8443 {
		stream_close_delay 30s
	}
}
```

`stream_close_delay` keeps a WebSocket or other stream open for 30s across a reload. It needs
Caddy 2.7 or later, which the official image and Coolify's Caddy are. A Caddy that runs as
`caddy.service` gets the block without it, because the Debian and Ubuntu package is 2.6.2 on
noble and refuses it.

Your Caddy reaches the switchboard by name on `network`, or on `127.0.0.1:<port>` without one. A
Caddy in a container with no `network` must run with `network_mode: host`, because the loopback of
any other container is its own, and bootstrap refuses one that doesn't. Because ocel's block names
each hostname, your Caddy gets a certificate for each, preview hostnames included, as they are
claimed; there is no wildcard.

Before placing the file, ocel runs `caddy adapt` on it alone, inside `container` or as
`/usr/bin/caddy`, and refuses a claim whose file your Caddy can't read. It is placed through the
switchboard, which is the only thing ocel runs with that directory mounted. Then ocel reloads
your Caddy in its own environment, where `{$VAR}` placeholders in your Caddyfile resolve:

| Caddy runs | Reload |
| --- | --- |
| in `container` | `docker exec <container> caddy reload --config <config> --adapter caddyfile` |
| in Coolify's `coolify-proxy` | `docker exec coolify-proxy caddy reload --config /config/caddy/Caddyfile.autosave`, Coolify's own |
| as `caddy.service` | `sudo -n /usr/bin/systemctl reload caddy.service`, through the one line bootstrap writes to `/etc/sudoers.d/ocel-caddy-reload` |

A reload your Caddy refuses leaves its old config running. Ocel puts the previous `ocel.caddy`
back and refuses the claim with Caddy's error, which can come from your own Caddyfile. Ocel
reloads only when the hostnames change, never on a release. A reload can drop about one request
under load, and as `caddy.service` it also closes the WebSocket and other streaming connections
your Caddy is proxying.

`caddy reload` needs the admin endpoint, so bootstrap refuses a Caddy run with `admin off`.
Ocel also reads what your Caddy serves from it (`GET /config/apps/http/servers` on
`localhost:2019`, with `wget` inside `container`, or with the box's `curl` for `caddy.service`,
so bootstrap refuses a box without `curl` there) and never takes a hostname your Caddy already serves: a bind is refused when a
host matcher outside ocel's block equals the hostname or is a wildcard that covers it, naming the
server and route. Two sites for one hostname would otherwise either fail your whole config or
shadow one another by file order. `ocel doctor` runs the same read, and also checks that your
Caddy serves ocel's hostnames, that `ocel.caddy` is what ocel renders, and that each hostname
answers through the switchboard.

A hostname that leaves `ocel.caddy` is no longer renewed after the next reload, and your Caddy
deletes its certificate 14 days after it expires. `ocel destroy` removes `ocel.caddy`, reloads
your Caddy, and removes the sudoers line. Your Caddyfile is never written.

The switchboard hears your Caddy on a listener of its own, which takes every request as https,
sets `X-Forwarded-Host` to `Host`, and drops every `X-Forwarded-*` header it is sent. Any
container on `network`, which on Coolify is every app it runs, can send a plaintext request
there that your apps take as https, for a `Host` it could send anyway. None can choose
`X-Forwarded-Host` or `X-Forwarded-For`.

## Postgres

`postgres("main")` runs as one container on the box, on your project's own network. It
publishes no port on the machine, so only your project's apps reach it. Its data lives on a
docker volume, and its password is generated on the first deploy and kept sealed on the box.

A [transform](/docs/transforms#on-a-vps) changes what runs: the image, its arguments, its
memory, where the volume lives.

**Backups.** The box dumps every postgres once a day and keeps the newest seven under
`/var/lib/ocel/<tier>/backups/<container>/`. Take one now, or read one back, on the box:

```bash
sudo /usr/local/lib/ocel/backups production dump <container> main
sudo /usr/local/lib/ocel/backups production restore <container> main <file>
```

`docker ps --filter label=ocel.resource` names the container. The dumps are on the same disk
as the database, so copy them somewhere else if losing the machine must not lose the data.

**Changing the version.** Moving `version` to a newer major dumps the running database,
starts the new version on a fresh volume, and restores into it. The database is down while
that runs. If any step fails, the old version is started again on the data it had.

**Removing it.** `ocel destroy` takes the container, its volume, its password and its dumps.

## Buckets

A bucket runs in a store the box keeps for the project. Bind it to a store you already run and
the box keeps none for it. See [Bucket](/docs/sdk/bucket#on-a-vps).

## Options

| Option | What it does |
| --- | --- |
| `ssh` | The machine to deploy onto: a `Host` alias, or an object of `host`, `user`, `port` and `identityFile`. |
| `deployKey` | The public key the `ocel-deploy` login is to answer to, as a path. Omit it and bootstrap mirrors the keys the login it bootstraps with already answers to. |
| `certificates` | Paths on the machine to the certificate to serve a hostname with, keyed by hostname. Refused alongside `proxy`. |
| `proxy` | What fronts the machine on ports 80 and 443. Omit it and ocel runs its own. `"manual"` puts ocel [behind your own proxy](#behind-your-own-proxy); [the `proxy` option](#the-proxy-option) lists every form. |
