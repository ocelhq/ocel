---
title: VPS
description: Deploy to any Linux box.
---

```bash
ocel init --provider vps
```

Name the machine ocel deploys onto — a `Host` alias from your `ssh_config`, or the
destination spelled out:

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "vps": { "ssh": { "host": "${DEPLOY_HOST}", "user": "deploy" } }
  },
  "apps": [{ "name": "web", "path": ".", "compute": "container" }]
}
```

Then:

```bash
ocel bootstrap production
ocel deploy
```

Bootstrap creates the `ocel-deploy` login every later deploy acts as.

## Bootstrap

`ocel bootstrap <class>` prepares the machine once per class (`production`, `preview`).
Running it again changes only what has drifted, and `ocel destroy` removes it all.
If something else already holds port 80 or 443, bootstrap names it and stops before it
changes anything: stop it, or run ocel [behind it](#behind-your-own-proxy).

| What | Why |
| --- | --- |
| `ocel-deploy` login, `/var/lib/ocel/.ssh/authorized_keys` | Every deploy logs in as this account. The keys are copied from the login you bootstrap with, or taken from `deployKey`. |
| `/etc/ocel/<class>/seal.key`, `/usr/local/lib/ocel/seal`, a sudoers line | Secret values are sealed to a key that never leaves the machine. `ocel-deploy` may run the seal helper as root and nothing else. Lose the key and the values can't be opened again. |
| `/var/lib/ocel/<class>/records`, `/usr/local/lib/ocel/records` | What is deployed, per class. |
| `/var/lib/ocel/releases`, `/usr/local/lib/ocel/releases` | The release window: which images a rollback can still reach. Older images are swept. |
| Docker | Installed once with Docker's install script, pinned by sha256. A Docker 28.0 or later that `docker.service` already runs is used as it is. Either way, upgrading it is yours. Bootstrap refuses a Docker older than 28.0, the snap package, a rootless Docker, and a masked `docker.service`, and says what to change. Docker stays after `ocel destroy`, and so do its containers. |
| `/var/lib/ocel/proxy.json` | Which proxy fronts the box, and which project and class set it. A deploy whose `proxy` option disagrees is refused. |
| `ocel-proxy` container, `/var/lib/ocel/proxy/caddy.json` | Caddy on ports 80 and 443. It gets a certificate for a hostname the box serves the first time a client connects to it. Left out [behind your own proxy](#behind-your-own-proxy). |
| `ocel-switchboard` container, the `ocel` network, `/usr/local/lib/ocel/switchboard`, `/run/ocel-switchboard`, `/run/ocel-front` | Routes each hostname to the app that serves it, and tells the proxy which hostnames it may get a certificate for. Behind your own proxy it is published on `127.0.0.1:8480`. |
| `/var/lib/ocel/routing/table.json` | The routing table: which project claims each hostname, where each app is served from, and the certificates you pin. Deploys rewrite it and the proxy's config together. |
| `/var/lib/ocel/proxy/data` | Certificates, their keys and the ACME account key. A certificate for a hostname the box stopped serving stays until it has been expired for 14 days, when Caddy removes it. If Caddy still holds that certificate in memory when it removes it, the next TLS connection for the hostname can get a new certificate without the switchboard's confirmation. A restart of `ocel-proxy` clears that memory. Left out behind your own proxy. |
| `/etc/ocel/certs` | Certificates you pin yourself. The proxy serves a pinned certificate for every hostname it covers, ahead of any certificate it got itself, and gets none of its own for those hostnames. Left out behind your own proxy. `ocel destroy` removes the directory only if it is empty. |
| `ocel-live.socket`, `ocel-live.service` | Serve each app container its secret values over a unix socket. |
| `ocel-backups.timer` | Dumps every resource once a day, and at boot if a day was missed. |

## Behind your own proxy

If the machine already runs a proxy on ports 80 and 443, ocel can sit behind it instead of
running its own:

```json title="ocel.json"
{
  "$schema": "https://ocel.dev/schema/0.0.0/ocel.schema.json",
  "slug": "my-app",
  "provider": {
    "vps": { "ssh": "prod", "proxy": "manual" }
  },
  "apps": [{ "name": "web", "path": ".", "compute": "container" }]
}
```

Bootstrap then stands no `ocel-proxy`. The switchboard, which routes each hostname to its
app, listens on `127.0.0.1:8480`. Name another port with
`"proxy": { "manual": { "port": 9000 } }`. Ocel never writes to your proxy. You route each
hostname yourself, and `ocel domain add` prints the route it needs:

```
Route shop.example.com → http://127.0.0.1:8480 (keep Host, set X-Forwarded-Proto)
```

A catch-all works too. In nginx:

```nginx
client_max_body_size 0;

location / {
    proxy_pass http://127.0.0.1:8480;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

A proxy running in a container can't reach the host's loopback. Put it on the `ocel` network
and forward to `http://ocel-switchboard:8080`. `docker network connect ocel <container>` does
that until the container is recreated: `docker compose up` recreates it whenever its
definition changes, and the new container is back on its own networks only. Declare the
network in the compose file instead, so every container compose creates joins it:

```yaml title="compose.yaml"
services:
  proxy:
    networks: [default, ocel]

networks:
  ocel:
    external: true
```

Bootstrap creates the `ocel` network, or uses the one already there. To start your proxy
before bootstrapping, create it yourself with `docker network create ocel`.

After printing the route, `ocel domain add` waits until the box proves it: a request to
`127.0.0.1:443` for the hostname must come back from ocel, with a certificate that covers the
name, `X-Forwarded-Proto: https`, and the hostname in `Host` and in `X-Forwarded-Host` if your
proxy sets it. A preview base asks for `*.<base>` and is proved on `ocel-edge-probe.<base>`.

The switchboard keeps `X-Forwarded-Proto` and `X-Forwarded-Host` from your proxy, because apps
build their URLs from them. It hears them only from the `ocel` network, which the loopback
port arrives on, and never from your apps' own networks. It never takes `X-Forwarded-For` from
your proxy: every process on the machine reaches the same port, so any of them could claim to
be any client. Apps see your proxy's address as the client.

Your proxy holds the certificates, so `certificates` and `proxy` can't be set together. One
proxy fronts a box. Every project on it must name the same `proxy`, and a deploy that
doesn't is refused with the value to write. Moving a box from one proxy to another isn't
supported yet. `"coolify"`, `"dokploy"`, `{ "traefik": … }` and `{ "caddy": … }` are
reserved and refused for now.

| | Ocel's own proxy | `manual` |
| --- | --- | --- |
| Holds ports 80 and 443 | ocel | you |
| Issues and renews certificates | ocel, over http-01 | your proxy |
| Serves the certificates you pin | yes | no, configure them in your proxy |
| Forgets a certificate when a hostname goes | yes | no, your proxy keeps it |
| Reports a Let's Encrypt rate limit | yes | no |
| Answers every preview hostname under a base | yes | once you route `*.<base>` |
| Switches releases without dropping requests | yes | yes, the switchboard does it |

## Postgres

`postgres("main")` runs as one container on the box, on your project's own network. It
publishes no port on the machine, so only your project's apps reach it. Its data lives on a
docker volume, and its password is generated on the first deploy and kept sealed on the box.

A [transform](/docs/transforms#on-a-vps) changes what runs: the image, its arguments, its
memory, where the volume lives.

**Backups.** The box dumps every postgres once a day and keeps the newest seven under
`/var/lib/ocel/<class>/backups/<container>/`. Take one now, or read one back, on the box:

```bash
sudo /usr/local/lib/ocel/backups production dump <container> main
sudo /usr/local/lib/ocel/backups production restore <container> main <file>
```

`docker ps --filter label=ocel.resource` names the container. The dumps are on the same disk
as the database, so copy them somewhere else if losing the machine must not lose the data.

**Changing the version.** Moving `version` to a newer major dumps the running database,
starts the new version on a fresh volume, and restores into it. The database is down while
that runs. If any step fails, the old version is started again on the data it had.

**Removing it.** `ocel destroy` takes the container, its volume, its password and its dumps.

## Buckets

A bucket runs in a store the box keeps for the project. Bind it to a store you already run and
the box keeps none for it. See [Bucket](/docs/sdk/bucket#on-a-vps).

## Options

| Option | What it does |
| --- | --- |
| `ssh` | The machine to deploy onto: a `Host` alias, or an object of `host`, `user`, `port` and `identityFile`. |
| `deployKey` | The public key the `ocel-deploy` login is to answer to, as a path. Omit it and bootstrap mirrors the keys the login it bootstraps with already answers to. |
| `certificates` | Paths on the machine to the certificate to serve a hostname with, keyed by hostname. Refused alongside `proxy`. |
| `proxy` | What fronts the machine on ports 80 and 443. Omit it and ocel runs its own. `"manual"` puts ocel [behind your own proxy](#behind-your-own-proxy). |
