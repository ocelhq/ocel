```bash
ocel preview                          # deploy the current branch's preview
ocel preview up pr-12
ocel preview up staging --persistent
ocel preview ls
ocel preview rm pr-12
```

A preview is a full deployment beside production, on its own hostname, torn down without touching
anything else. It needs `ocel bootstrap preview` and a preview domain.

- `ls` lists each preview's name, lifecycle, label, alias URL and creation time.
- `prune` keeps the newest `--keep` deployments (3 by default) and whatever is live.
- `rm` asks first for a persistent preview. Without a terminal it stops unless you pass `--yes`.

## Naming a preview

With no name, a command addresses the current branch's preview, taking the branch from
`GITHUB_HEAD_REF` on CI's detached HEAD, and stops when it has neither.
[`ocel logs --preview`](/docs/cli/logs) does the same. A name works from any branch or machine: a DNS
label (lowercase letters, digits and hyphens, starting with a letter) with no `--`, after a
subcommand.

```yaml title=".github/workflows/preview.yml"
- run: ocel preview up pr-${{ github.event.number }}
- run: ocel preview prune pr-${{ github.event.number }}
```

## Hostnames

| Hostname | Serves | Until |
| --- | --- | --- |
| The alias | The preview's newest deployment | `ocel preview rm` |
| A deployment's own | That deployment only | `prune` or `rm` drops it |

`up` prints both. The alias is fixed at creation, so a build already knows it, and changes only
with the preview domain or when the project goes from one app to several or back.

| Preview domain | Hostname |
| --- | --- |
| The project's `domains.preview` | `pr-12-web-<token>.preview.example.com`: name, then the app when there are several |
| The global preview domain | `shop-<token>.preview.example.com`: the project's slug |

The random token keeps URLs unguessable from the name or branch (on Cloudflare it is signed, and
the edge turns a made-up one away at once). That is not access control: URLs leak through pull
request comments, chat previews and `Referer` headers, so keep secrets out of previews, or
[protect them](#protecting-previews).

## Protecting previews

```bash
ocel preview protection
ocel preview protection password
ocel preview protection password rotate
printf '%s' "$PREVIEW_PASSWORD" | ocel preview protection password set
ocel preview protection bypass create
ocel preview protection bypass ls
ocel preview protection bypass revoke <id>
ocel preview protection sync
```

Whether a project's previews ask for a password is one switch in its config,
[`previews.protection`](/docs/configuration#previews), and every preview deploy enforces it. With
it on, the first preview deploy creates a password and never prints it; with it off or left out,
the next preview deploy opens the previews again and says so. It keeps the password and the bypass
secrets, so turning protection back on restores them. The commands above never turn protection on or
off. They show the password, replace it, and manage the bypass secrets a machine can send in its
place. Each refuses while the config does not protect previews, and while the last preview deploy
left them open, until a preview deploy with protection on restores them.

A visitor to a protected preview gets a login page; entering the password opens a session for
seven days. A request that carries the password as HTTP Basic credentials, with any user name, or
a bypass secret in the `x-ocel-preview-bypass` header, passes without a session, and a bypass
request that also sends `x-ocel-set-bypass-cookie: true` is answered with a redirect that opens one.
A request that fails never reaches your app, and neither does the password. Without JavaScript the
login page offers the browser's own password prompt.

`ocel preview protection` says whether protection is on and why, whether a password is set, which
bypass secrets exist by id, and for the edge that serves the project's previews whether it holds the
current credentials. `password` prints the password alone, so it pipes. `password rotate` replaces it
with a generated one and prints it; `password set` takes one you choose from standard input, of at
least 12 characters and at most 256 bytes. Both end every login session. `bypass create` prints a
secret once; a project holds at most eight, and `bypass revoke` ends one along with every session.
Creating a bypass secret leaves sessions alone.

A change is recorded and then published to the edge, so it takes effect without a deploy. The
Cloudflare worker may serve the old credentials for up to five seconds, and a GCP load balancer
takes a few minutes to roll its gate plugin out. A Cloud Run service with no edge in front
reads its gate from a mounted secret at most five seconds after it last read it, and
[Configure secrets for services](https://docs.cloud.google.com/run/docs/configuring/services/secrets)
says Cloud Run fetches a mounted secret from Secret Manager each time it is read. If an edge cannot be reached the command still
prints any secret it generated, exits with an error, and leaves the edge shown as pending until
`ocel preview protection sync` publishes the recorded credentials again.

An edge has to run the gate for a project to be protected on it, and a deploy through one that does
not is refused. On GCP a preview served on its own Cloud Run URL is gated by its own service: the
gate lives in a Secret Manager secret that every container and Node, Next or SvelteKit function of
the project's previews mounts, even while protection is off, so turning it on or changing the
credentials reaches the running instances without a deploy. A Go, Python or Rust function checks no
gate: a protected preview with one is refused, and while an unprotected one is still deployed,
`ocel preview protection` names it rather than calling the previews protected. A change or
`ocel preview protection sync` then still writes the gate to every service that checks it, and
exits with an error naming those functions, until those previews are destroyed.

## Ephemeral and persistent

A preview is ephemeral unless created with `--persistent`, and keeps that lifecycle: deploying the
other one to the same name is refused, so remove it first or use another name.

| | Ephemeral | Persistent |
| --- | --- | --- |
| Infrastructure | None of its own, only what [bindings](/docs/cli/bindings) share | Its own database, bucket and the rest |
| Teardown | `rm` tears it down straight away | `rm` asks first, and needs `--yes` in CI |

If an ephemeral preview's app declares a resource no binding covers, the deploy stops: pass
`--persistent`, or add a binding with `ocel bindings set --preview`.
