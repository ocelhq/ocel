# Terraform Plugin Framework: what the framework owns, what a provider writes

## Short answer

- The split is protocol-and-state versus effects. The framework serves gRPC, answers `GetProviderSchema`, decodes and encodes config/plan/state against the declared schema, decides from state+plan whether an apply is a `Create`, `Update` or `Delete`, and removes the resource from state after a clean `Delete`. The author writes methods that call the remote API and set response state. Ocel's kit should hold the same line: the kit owns the wire, the vendor package owns the calls.
- Required surface is one small interface; every extra capability is a separate interface found by type assertion at call time. `resource.Resource` is six methods; import, configure, plan modification, config validation, state upgrade and identity are each a `ResourceWith*`. Adding a capability means adding a method set, never editing a registration struct or a capability bitfield.
- An unimplemented optional produces a diagnostic, not a panic or a missing RPC: import asserts, and on failure returns "This resource does not support import. Please contact the provider developer for additional information." A kit's capability probe should read the same way.
- Provider-level clients reach resources through one untyped field. `Configure` sets `resp.ResourceData`; each resource receives it as `any` and asserts. Ordering is not guaranteed — validation RPCs run without `ConfigureProvider` — so every resource opens with a nil guard. Ocel can pass credentials the same way but make the type concrete, having no SDKv2 to stay compatible with.
- `main()` is four lines: build the provider, name it by registry address, call `providerserver.Serve`. Protocol version, debug process lifecycle and the plugin handshake are `ServeOpts` fields, not author code.
- Multiplexing is a server-level wrapper, not a provider feature: `tf6muxserver.NewMuxServer` combines N servers under one address, on the conditions that provider schemas match and no resource type is claimed twice. That is the shape to copy if one Ocel binary must front two vendor packages.
- Conformance ships as a harness, not a checklist. `terraform-plugin-testing` drives a real Terraform CLI binary through plan/apply/refresh/destroy against the author's provider, wired in by one field holding `providerserver.NewProtocol6WithError(newProvider())`. Each step implicitly asserts an empty follow-up plan and `CheckDestroy` runs at the end — the Ocel equivalent is a driver that runs deploy → verify → redeploy → teardown against a vendor package and asserts idempotence.
- Unit tests here are for helpers, not resources; correctness lives in the acceptance harness behind a `TF_ACC` opt-in so a plain `go test` cannot bill anyone. An Ocel conformance suite needs the same guard.
- Where the analogy stops: Terraform's unit is a resource with a declared schema and a diffed state, and most of the framework's weight is schema plumbing, plan modification and state upgrades. Ocel's wire is whole-release operations with no per-resource schema, so the kit inherits the interface shape and the harness, and none of the schema/plan/state machinery.

## 1. The division of labour

- The framework is HashiCorp's recommended SDK for protocol version 5 or 6, supplying provider servers that handle "all calls for provider, resource, and data source operations", plus providers, resources, data sources, schemas and functions. https://developer.hashicorp.com/terraform/plugin/framework
- `GetProviderSchema`: the framework calls `Schema` on the provider and every resource and data source. `ValidateResourceConfig`: it runs attribute validators, then `ConfigValidators`, then `ValidateConfig`. https://developer.hashicorp.com/terraform/plugin/framework/internals/rpcs
- `PlanResourceChange`: the framework fills defaults, and "All attributes that are null in the configuration are then marked as unknown in the plan so that a provider has the opportunity to update them", then runs attribute plan modifiers and finally `ModifyPlan`. `ApplyResourceChange`: the framework determines whether to call `Create`, `Update` or `Delete`; the provider "must implement `Create`, `Update` and `Delete` functions for each resource". https://developer.hashicorp.com/terraform/plugin/framework/internals/rpcs
- After a successful `Delete` the author is told to "Skip calling the response state `RemoveResource()` method. The framework automatically handles this logic with the response state if there are no error diagnostics." https://developer.hashicorp.com/terraform/plugin/framework/resources/delete
- `Read` is the drift path: Terraform calls `ReadResource` during `apply`, `plan` and `refresh`, and the author refreshes all values and, on a gone resource, calls "the response state `RemoveResource()` method, and return early". https://developer.hashicorp.com/terraform/plugin/framework/resources/read
- Consistency is enforced above the author: after `Update`, "all attribute state values must match their associated planned values or Terraform will generate a `Provider produced inconsistent result` error". https://developer.hashicorp.com/terraform/plugin/framework/resources/plan-modification

## 2. `provider.Provider` and its optional extensions

- `Provider` is "the core interface that all Terraform providers must implement": `Metadata`, `Schema`, `Configure`, `DataSources`, `Resources`. https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/provider/provider.go
- Optional extensions, each its own interface: `ProviderWithConfigValidators` (declarative validation), `ProviderWithValidateConfig` (imperative), `ProviderWithFunctions` (Terraform 1.8+), `ProviderWithEphemeralResources` (1.10+), `ProviderWithActions` (1.14+), `ProviderWithListResources`, `ProviderWithMetaSchema` (experimental), `ProviderWithStateStores` (experimental, no compatibility guarantee). https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/provider/provider.go
- A minimal provider is a struct with those five methods plus the compile-time assertion `var _ provider.Provider = &ExampleCloudProvider{}`; resources register as constructors, `Resources()` returning `[]func() resource.Resource{NewThingResource}`. https://developer.hashicorp.com/terraform/plugin/framework/providers, https://developer.hashicorp.com/terraform/plugin/framework/resources

## 3. `resource.Resource` and its optional extensions

- `Resource` is "the core interface that all resources must implement": `Metadata`, `Schema`, `Create`, `Read`, `Update`, `Delete`. https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/resource/resource.go
- Each optional capability is a one-method interface: `ResourceWithConfigure`, `ResourceWithImportState`, `ResourceWithModifyPlan`, `ResourceWithValidateConfig`, `ResourceWithConfigValidators`, `ResourceWithUpgradeState` (`UpgradeState(ctx) map[int64]StateUpgrader`), `ResourceWithMoveState` (`MoveState(ctx) []StateMover`), `ResourceWithIdentity` (`IdentitySchema`), `ResourceWithUpgradeIdentity`. https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/resource/resource.go
- Discovery is a runtime type assertion inside the server, and the miss is a diagnostic: `resourceWithImportState, ok := req.Resource.(resource.ResourceWithImportState)`, else `resp.Diagnostics.AddError("Resource Import Not Implemented", "This resource does not support import. Please contact the provider developer for additional information.")`. https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/internal/fwserver/server_importresourcestate.go
- Import is usually one line — `resource.ImportStatePassthroughID(ctx, path.Root("id"), req, resp)` — because the contract is only to "specify enough Terraform state for the `Read` method to refresh", and `Read` runs afterwards. https://developer.hashicorp.com/terraform/plugin/framework/resources/import
- State upgrades hang off `schema.Schema.Version`: when the saved version does not match the current one, Terraform requests an upgrade, the framework checks whether the resource defines one and errors if not, and "The framework does not copy any prior state data" — the upgrader populates everything. https://developer.hashicorp.com/terraform/plugin/framework/resources/state-upgrade
- Plan modifiers are the declarative half of plan control: `RequiresReplace()`, `RequiresReplaceIf()`, `RequiresReplaceIfConfigured()`, and `UseStateForUnknown()`, which "Copies the prior state value, if not null… useful for reducing `(known after apply)` plan outputs". Attribute modifiers run before `ModifyPlan`. https://developer.hashicorp.com/terraform/plugin/framework/resources/plan-modification

## 4. Handing provider clients to resources

- The provider sets `provider.ConfigureResponse.ResourceData` in `Configure`; the framework passes it to every resource implementing `ResourceWithConfigure`, the hook "which the framework will automatically call so provider developers have the opportunity to setup provider-level data or clients". https://developer.hashicorp.com/terraform/plugin/framework/resources/configure, https://raw.githubusercontent.com/hashicorp/terraform-plugin-framework/main/resource/resource.go
- The field is untyped, so the resource asserts and reports a typed error on mismatch: `client, ok := req.ProviderData.(*http.Client)` → `resp.Diagnostics.AddError("Unexpected Resource Configure Type", fmt.Sprintf("Expected *http.Client, got: %T.", req.ProviderData))`. https://developer.hashicorp.com/terraform/plugin/framework/resources/configure
- The nil guard is mandatory: "Terraform calling the `ValidateResourceConfig` RPC would not call the `ConfigureProvider` RPC first, so implementations need to account for that situation" — hence `if req.ProviderData == nil { return }`. https://developer.hashicorp.com/terraform/plugin/framework/resources/configure

## 5. `main()` and serving

- The whole binary entrypoint: `opts := providerserver.ServeOpts{Address: "registry.terraform.io/example-namespace/example"}`, then `providerserver.Serve(context.Background(), provider.New(version), opts)`, with `log.Fatal` on error. https://developer.hashicorp.com/terraform/plugin/framework/provider-servers
- "Serve serves a provider, blocking until the context is canceled." `ServeOpts` carries `Address` (hostname/namespace/type), `Debug` ("Runs the provider in a mode acceptable for debugging and testing processes, such as delve, by managing the process lifecycle") and `ProtocolVersion`, which "Defaults to protocol version 6". https://pkg.go.dev/github.com/hashicorp/terraform-plugin-framework/providerserver
- Protocol 6 needs Terraform CLI 1.0+ (1.1+ when mixed with SDK-based code); protocol 5 reaches back to 0.12 and is selected with `ProtocolVersion: 5`. https://developer.hashicorp.com/terraform/plugin/framework/provider-servers
- `NewProtocol5`/`NewProtocol6` produce a `ProviderServer` "suitable for usage with the… tf6server.Serve() function and various terraform-plugin-mux functions"; the `WithError` variants exist specifically for `helper/resource.TestCase.ProtoV6ProviderFactories`. https://pkg.go.dev/github.com/hashicorp/terraform-plugin-framework/providerserver

## 6. Muxing

- terraform-plugin-mux provides "combining (multiplexing) and translating provider servers" while "minimizing provider code changes by wrapping existing provider servers": `tf5muxserver`, `tf6muxserver`, `tf5to6server`, `tf6to5server`. Its stated purposes are supporting varying Terraform requirements from one codebase and migrating resources from SDKv2 to the framework over time. https://developer.hashicorp.com/terraform/plugin/mux
- The conditions are hard: "All provider schemas must match", "All provider meta schemas must match", "Only one provider may implement each resource and data source". The wiring is `tf6muxserver.NewMuxServer(ctx, providers...)` followed by `tf6server.Serve(address, muxServer.ProviderServer, serveOpts...)`. https://developer.hashicorp.com/terraform/plugin/mux/combining-protocol-version-6-providers

## 7. Testing

- Acceptance tests are the real thing: the harness "runs a local Terraform binary to perform real plan, apply, refresh, and destroy operations", selected by `TF_ACC_TERRAFORM_PATH`/`TF_ACC_TERRAFORM_VERSION` or downloaded. `TF_ACC` must be set to any value; it "Prevents developers from incurring unintended charges when running other Go tests". https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests
- The provider is injected as a factory: `ProtoV6ProviderFactories: map[string]func() (tfprotov6.ProviderServer, error){"examplecloud": providerserver.NewProtocol6WithError(newProvider())}`, because "The testing module must know how to reference your provider code before Terraform commands and configurations can succeed. This is achieved by pointing the testing module at a provider server which wraps your provider." https://developer.hashicorp.com/terraform/plugin/framework/acctests
- `TestCase` carries `PreCheck` ("will be called before any test steps are executed"), `TerraformVersionChecks`, `Steps`, and `CheckDestroy`, "called after all test steps have been run and Terraform has run destroy on the remaining state". https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests/testcase
- A `TestStep` is "a full terraform apply of a given configuration language, followed by zero or more checks", with an implicit empty-plan assertion after; `ImportState: true` makes a step an import test, `RefreshState: true` a refresh test, and assertions arrive as `ConfigPlanChecks` (against the plan file) and `ConfigStateChecks` (after apply). https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests/teststep
- Unit testing is scoped narrowly — "Testing plugin code in small, isolated units is distinct from Acceptance Tests, and does not require network connections", and is "commonly used for testing helper methods that expand or flatten API responses". No framework-supplied fake Terraform exists for resource-level unit tests. https://developer.hashicorp.com/terraform/plugin/testing/unit-testing
