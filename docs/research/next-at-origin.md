# Next at the origin without a programmable edge (#394)

Sources are the repo at HEAD `9cb9b4cc` and `next@16.2.10` as installed (compiled `dist/` line numbers; the TypeScript source lives at the same path under `packages/next/src/` in `vercel/next.js` tag `v16.2.10`). Next docs cited are the 16.3.1 pages; where 16.2.10 differs it is said.

## Short answer

1. The Lambda does not run `next start`. It invokes each route's compiled `handler(req, res, ctx)` directly (`platform/aws/functions/entrypoints/src/next/entrypoint.mts:30-55`, `frameworks/next/adapter/src/next-dispatch.cjs:241-274`). Nothing on the origin constructs `NextNodeServer` or the router-server, so `next start`'s middleware, edge-function sandbox, `_next/image`, static files, redirects/headers, trailing-slash and locale redirects do not exist there.
2. Node middleware (`runtime: 'nodejs'`) *is* shipped in the first Lambda bundle under entry key `/_middleware`, but it only runs when the request carries `x-ocel-entry: /_middleware` (`next-dispatch.cjs:243-261`); no pathname maps to it (`next-adapter.mts:136-151`). Only the entry worker sends that header (`platform/edge/cloudflare/workers/entry/src/index.ts:1693-1709`), and only the worker composes the returned `x-middleware-*` headers into a rewrite/redirect/next decision via `@next/routing` (`index.ts:649-733`). Without the worker, middleware never executes and pages render as if it did not exist.
3. Edge middleware and `runtime: 'edge'` routes are excluded from every Lambda bundle (`next-adapter.mts:106-107,158`) and exist only in `edge/bundle.json`, a Workers-shaped module graph (`renderEdgeShim`, `next-adapter.mts:553-616`) loaded through Cloudflare's `WorkerLoader` (`edge.ts:238-306`). With no programmable edge they do not execute anywhere today; the parity fallback ("run them on the origin as `next start` does") is not built.
4. PPR without a resumer: the origin already behaves like `next start`. `minimalMode` is set only for `POST` + `next-resume: 1` (`entrypoint.mts:17-19,51`); a plain GET runs the app-page handler in non-minimal mode, which reads shell + `postponed` from Ocel's S3-backed cache handler (`cache-handler.mts:138-153`; `postponed` is written at build, `next-adapter.mts:941-943`) and streams the shell then the resumed dynamic part in one response with `Cache-Control: private, no-cache, no-store` (`dist/build/templates/app-page.js:1197-1300`; `dist/server/lib/cache-control.js:14-15`). This is the "origin-only" level of Next's PPR platform guide, not a full dynamic re-render. Un-prerendered params go through the same handler's fallback-shell path (`app-page.js:663-720`).
5. To serve end-to-end the origin needs a front that: (a) picks the Lambda per pathname (a build can pack several bundles, `pack.mts:101-124`; static/public/`_next/static` live only in S3, `next-adapter.mts:262-279`, `platform/aws/provider/deploy/assets.go:27-31`); (b) runs `resolveRoutes` from `@next/routing` — redirects/headers/rewrites, trailing-slash 308, `_next/data` normalisation, locale detection/redirect, middleware matchers, `x-middleware-*` → rewrite/redirect/next/override, `x-matched-path`/`x-nextjs-data`/`x-ocel-entry` request headers (all of which the worker does today: `index.ts:590-754,900-922`, `trailing-slash.ts`, `i18n.ts`); (c) proxies `_next/image` to the image-optimizer Lambda (`index.ts:478-499`, `platform/aws/functions/image-optimizer/`); (d) prerender/ISR serving is already origin-native via the cache handler, so it needs nothing beyond (a). Once (a)-(c) exist, node middleware and PPR work at the origin; edge middleware/routes still need a Node-side runner (Next's own is `dist/server/web/sandbox`, used by `next-server.js:1206,1320`).

## Detail

### What runs in the Lambda

- `entrypoint.mts:30-36` imports the launcher written by the adapter (`renderLauncher`, `next-adapter.mts:1038-1062`), which wraps `next-dispatch.cjs`. `next-dispatch.cjs:241-274` selects an entry by `x-ocel-entry` or by pathname against `ROUTES` (`exact` = nodejs route keys, `dynamic` = `routing.dynamicRoutes` regexes, `next-adapter.mts:1005-1020`) and calls the Next entry's `handler(req, res, ctx)`. That is the adapter contract Next documents for Node entrypoints (https://nextjs.org/docs/app/api-reference/adapters/invoking-entrypoints).
- The app-page template's `handler` does per-route work only: `routeModule.prepare` strips `basePath`, normalises `_next/data` and locale prefixes, applies `next.config` rewrites and extracts params (`dist/server/route-modules/route-module.js:360-470`), then renders/serves from the incremental cache (`app-page.js:896-1300`). It never redirects for trailing slash or locale (no redirect logic in `route-module.js`), never runs middleware, and never serves static files or `_next/image`.
- Next places all of those in the server, not the entrypoints: `next start` → router-server → `resolve-routes.js` handles trailing slash (`:128`), i18n (`:140-164`), middleware invocation and `x-middleware-*` interpretation (`:333-520`); `next-server.js` runs middleware and edge routes through `./web/sandbox` (`:1107-1206`, `:1278-1321`) and serves `_next/image` (`:153-250`). Next's runtime-integration doc states the split: the adapter is build-time; "Runtime behavior (request handling, streaming, caching) is handled by the Next.js server itself" (https://nextjs.org/docs/app/api-reference/adapters/runtime-integration).
- `experimental.trustHostHeader: true` is forced by the adapter (`next-adapter.mts:60`) so the handler builds absolute URLs from `host`, which the membrane sets from `x-forwarded-host` (`platform/aws/functions/entrypoints/src/shared/membrane.mts:153-159`). Requests reach the Node server through the Go bootstrap from an IAM-authenticated Function URL (`platform/aws/provider/deploy/function.go:463-467`, `platform/aws/provider/cmd/lambdanode/bootstrap/forward.go:125-135`); the worker signs them (`index.ts:1866-1869`). No API Gateway or CloudFront resource exists in `platform/aws` today.

### Middleware

- Adapter output: node middleware seeds the first bundle (`next-adapter.mts:90,158-164`) and its entry is registered under `/_middleware` (`:223-227`); the routing manifest records `runtime`, bundle `id`, `entryKey`, `matchers` (`:449-462`).
- Origin side: `runMiddleware` (`next-dispatch.cjs:46-104`) calls the Next middleware adapter function with a `nextConfig` projection, then writes the raw `Response` back plus `x-ocel-middleware-headers` naming which headers the middleware authored. It does not act on `x-middleware-rewrite`/`-redirect`/`-next`/`-override-headers` — those are set by `NextResponse` (`dist/server/web/spec-extension/response.js:36-39,118,127`) and re-mapped by Next's adapter (`dist/server/web/adapter.js:287-385`), and interpreted by whoever routes.
- Worker side: `invokeMiddleware` (`index.ts:1688-1716`) forwards to the middleware bundle's Function URL with `x-ocel-entry: /_middleware`, then `responseToMiddlewareResult` (from `@next/routing`) turns the response into the routing decision inside `resolveRoutes` (`index.ts:706-727`); `dispatch` applies `middlewareResponded`, `redirect`, `externalRewrite`, override headers (`index.ts:993-1007,1294-1309`).
- Docs: "Proxy defaults to using the Node.js runtime" and the `runtime` option is not available in proxy files (v16.0.0 row of the version table, https://nextjs.org/docs/app/api-reference/file-conventions/proxy#runtime). It "works self-hosted with zero configuration when deploying using `next start`" (https://nextjs.org/docs/app/guides/self-hosting#proxy). Platform support for adapters is "Platform-specific". Middleware output carries `runtime: 'nodejs' | 'edge'` and `edgeRuntime` for the edge case (https://nextjs.org/docs/app/api-reference/adapters/output-types#middleware-outputsmiddleware).

### `runtime = 'edge'` routes

- `edgeRoutes` are separated at `next-adapter.mts:107` and never passed to `packBundles`; they are dispatched as `kind: "edge"` (`:314-318`) and bundled by `emitEdgeBundle` (`:673-770`) into `edge/bundle.json` whose shim is a Workers `export default { fetch }` reading `ctx.props.entryKey` and `globalThis._ENTRIES` (`:593-615`). Prerenders parented by edge routes have `edgeEntryKey` and their revalidation is inert (`:112-119,1330`).
- The worker invokes them via `createEdgeInvoker` (`edge.ts:238-306`) using `WorkerLoader`; with no `LOADER` binding `deps.edge` is undefined and the response is a 500 "Edge invocation failed" / "no edge runtime is bound" (`index.ts:1712-1715,1732-1745`).
- Next 16.3.x docs mark the Edge Runtime deprecated for routes ("Remove the `runtime` export", https://nextjs.org/docs/messages/edge-runtime-deprecated; https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/runtime). The installed 16.2.10 build contains no `edge-runtime-deprecated` string, so the pinned version still builds them silently. Next's Node server executes them in `dist/server/web/sandbox` (`next-server.js:1320`); Ocel ships no equivalent runner in the Lambda.

### PPR

- Build: `postponedState` is stored alongside the shell in the emitted cache entry (`next-adapter.mts:941-943`) and `pprChain`/`renderingMode` land in the dispatch table (`:379`, `index.ts:211-218`), matching Next's guidance to store shell + state atomically (https://nextjs.org/docs/app/guides/ppr-platform-guide#storing-ppr-artifacts).
- Origin: `minimalMode` is only set for a resume (`entrypoint.mts:17-19,51`). In non-minimal mode `app-page.js` reads the cache entry (`:896-919`), and when `didPostpone && !isMinimalMode && !isRSCRequest` streams the shell and pipes a second render seeded with `cachedData.postponed` into the same response (`:1247-1300`) with `cacheControl.revalidate = 0` → `private, no-cache, no-store, max-age=0, must-revalidate` (`cache-control.js:14-15`). Next's guide calls this the origin-only implementation: "The server reads the shell from its local cache, sends it, then renders and streams the dynamic content. This is what `next start` does by default." (https://nextjs.org/docs/app/guides/ppr-platform-guide#origin-only-implementation). Ocel's cache handler returns `postponed` from S3 (`cache-handler.mts:96-113,138-153`), so the origin needs no full dynamic re-render; a re-render happens only on a cache miss (fallback shell path, `app-page.js:663-720`, then resume as above).
- Edge: the worker composes the R2/edge shell with a `POST` + `next-resume: 1` resume (`ppr.ts:19-51`, `index.ts:1421-1457`), which is Next's CDN-to-origin resume protocol (https://nextjs.org/docs/app/guides/ppr-platform-guide#the-resume-protocol). Losing the resumer costs TTFB (shell from region instead of edge), not correctness — the doc's degradation clause: "fall back to a full server render. The user gets a complete page without the shell-first optimization." (ibid., checklist item 5).
- Streaming caveat from Next: PPR needs end-to-end streaming; "AWS ALB with Lambda integration may buffer responses by default" (https://nextjs.org/docs/app/guides/self-hosting#streaming-and-suspense). Whether the chosen `none`/native front streams is a property of that front, not of Next; the Function URL invoke mode is set per function (`function.go:466`).

### What the origin front must gain (gap list against the worker)

| Concern | Worker today | Origin/Lambda today |
| --- | --- | --- |
| Pick function per pathname | manifest `dispatch` + `functionUrls` (`index.ts:1093-1101`) | per-bundle `ROUTES` only (`next-dispatch.cjs:175-181`); cross-bundle unknown |
| Static, public, `_next/static`, pages `.html` | `serveStaticAsset` from R2 with hashes (`assets.ts`) | none; files are in S3 (`assets.go:27-31`) |
| Repeated-slash / trailing-slash 308, `_next/data` shape | `trailing-slash.ts`, `index.ts:597-614` | none |
| Locale detection/redirect, locale-prefixed routing | `i18n.ts`, `index.ts:631-644,677-705` | locale *strip* only in `route-module.js:395-438` |
| `next.config` redirects/headers/rewrites | `resolveRoutes` (`index.ts:649-663`) | rewrites only, in `route-module.js:427-438` |
| Middleware execute + `x-middleware-*` | `index.ts:664-732,1688-1716` | executes only on `x-ocel-entry`; result not interpreted |
| Edge middleware / edge routes | `WorkerLoader` (`edge.ts`) | absent from bundles |
| `_next/image` | proxy to optimizer Lambda (`image.ts`) | absent |
| Prerender/ISR serving | R2 + colo cache + interception | native via cache handler (non-minimal mode) |
| PPR shell + resume | edge shell + `next-resume` POST | native single-pass |
| Error page substitution, 405 on document POST | `index.ts:1032-1046,1185-1233` | Next's own 404/500 rendering inside the handler |
