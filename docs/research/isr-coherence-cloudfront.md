# ISR coherence on CloudFront

Ticket: ocelhq/ocel#395 (part of #390). Researched 2026-08-17.

## Short answer

- Use CloudFront **invalidation by cache tag** (GA 2026-04-29): the origin returns the page's Next tags in a response header named by the distribution's `CacheTagConfig`, and one `CreateInvalidation` item `#<tag>` clears every cached variant (HTML, `_rsc`, query, header variants) that carries it. `revalidatePath` is already a single soft tag `_N_T_<path>[/page|/layout]`, so every Next revalidation call maps to one invalidation item.
- Latency: AWS states tag invalidations "take effect in under 5 seconds at P95" and report complete "under 25 seconds at P95". No SLA is published for any invalidation kind. Ocel's own hop (DynamoDB stream → publisher Lambda) adds ~0.25–1 s. Native mode can promise **"edge coherent within ~10 s (typical), no contractual bound"** — the same class as the Cloudflare edge's 6–10 s tag-clock snapshot.
- Cost: `$0.005` per invalidation item after the first 1,000 items per month per AWS account (paths and tags share the pool, aggregated across all distributions). One `revalidateTag`/`revalidatePath` = one item, regardless of how many pages it clears. Default rate quota: 150 paths-or-tags per second.
- Cache-key versioning through CloudFront Functions + KeyValueStore is possible for a header-in-cache-key scheme, but it needs a tag→path map at write time (Ocel does not keep one), is capped at 5 MB per store, serialises writers on an ETag, and has only "a few seconds" propagation with no figure. It is not the answer for tags; it is not needed now that tag invalidation exists.
- `s-maxage` clamping (Cache Policy Max TTL = bound) is the only mechanism with a hard bound, at the price of an origin revalidation per POP/regional cache per window; it is a fallback, not the design.
- Two origin-side facts constrain the implementation: (1) Next emits `x-next-cache-tags` only in `minimalMode`, which Ocel does not run (it would also silence `x-nextjs-cache`, the revalidator's receipt), so Ocel must add the tag header itself from the cache entry it already holds; (2) after `revalidateTag(tag, 'max')` the origin's next response is `STALE` and still carries the full `s-maxage`, so a naive invalidation re-caches stale content — the origin must shorten `Cache-Control` on `x-nextjs-cache: STALE` responses (or the invalidation must follow the re-render).
- CloudFront stores at most 50 tags per object (Next allows 128) and matches tags case-insensitively (Next tags are case-sensitive); the header must be truncated deterministically with the soft tags first (Next already orders them first).

## 1. What Next.js does and expects

- ISR responses carry `s-maxage={revalidate}, stale-while-revalidate={expire - revalidate}` (default `expire` one year); static `s-maxage=31536000`; dynamic `private, no-cache, no-store, max-age=0, must-revalidate`. "CDN-level caching alone does not support on-demand revalidation … the CDN will continue serving its cached copy until the `s-maxage` TTL expires. To propagate on-demand revalidation to the CDN, trigger CDN purges alongside your revalidation call … (including both HTML and RSC variants)." — https://nextjs.org/docs/app/guides/cdn-caching
- The formatting is `s-maxage=${revalidate}${swr}` from the entry's `cacheControl`, independent of whether the entry is stale — installed Next 16.2.10, `dist/server/lib/cache-control.js:13-19`, and `dist/build/templates/app-page.js:997-1011` (cacheControl taken from `cacheEntry.cacheControl`, not from `isStale`).
- `x-nextjs-cache: HIT|STALE|MISS|REVALIDATED` is set only when `!isMinimalMode` — `dist/build/templates/app-page.js:958-962`. `x-next-cache-tags` is set on the response only when `isMinimalMode && isSSG` — `app-page.js:1035-1037`, `1085-1088`, `1105-1108`. The tags are otherwise kept in the cache entry's `headers` (`app-page.js:581-583`); Ocel's origin cache handler already reads them (`platform/aws/functions/entrypoints/src/next/cache-handler.mts:147`). Ocel runs non-minimal except for PPR resume (`platform/aws/functions/entrypoints/src/next/entrypoint.mts:51`).
- Header content: implicit soft tags are seeded first (`dist/server/app-render/app-render.js:749-750`), joined with `,` (`app-render.js:1626-1628`); `NEXT_CACHE_TAG_MAX_ITEMS = 128`, `NEXT_CACHE_TAG_MAX_LENGTH = 256`, `NEXT_CACHE_IMPLICIT_TAG_ID = '_N_T_'` (`dist/lib/constants.js:275-283`; also https://github.com/vercel/next.js/blob/canary/packages/next/src/lib/constants.ts). Soft tags: `_N_T_/layout`, `_N_T_/blog/layout`, …, `_N_T_/blog/hello` — https://nextjs.org/docs/app/guides/how-revalidation-works
- `revalidatePath(path, type?)`: pages invalidate the specific page; layouts invalidate everything beneath; a literal path is one tag, `'page'`/`'layout'` select the `/page` or `/layout` soft tag; effect is on next visit — https://nextjs.org/docs/app/api-reference/functions/revalidatePath
- `revalidateTag(tag, 'max')`: "The tag entry is marked as stale, and the next time a resource with that tag is visited, it will use stale-while-revalidate semantics" ; `{ expire: 0 }` / `updateTag` expire immediately (blocking render). Tag ≤ 256 chars, case-sensitive — https://nextjs.org/docs/app/api-reference/functions/revalidateTag
- Multi-instance coordination via `updateTags()` / `refreshTags()` on the cache handler; "CDN integration: If a CDN caches Next.js responses, it should respect the `Vary` header and the `Cache-Control` directives" — https://nextjs.org/docs/app/guides/how-revalidation-works
- Next generates ETags for every page by default (`generateEtags`) — https://nextjs.org/docs/app/api-reference/config/next-config-js/generateEtags

## 2. CloudFront invalidation: cost, quotas, latency

- Two paths: invalidate, or version file names. AWS recommends versioning for frequent updates because it is cheaper and controls downstream caches; invalidation is the tool when the URL cannot change — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html
- Price: "No additional charge for the first 1,000 paths or tags requested for invalidation each month. Thereafter, $0.005 per path or tags requested" — https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/ . The 1,000 free items are per AWS account across all distributions; a wildcard or a tag item counts as one regardless of objects cleared; items in one batch are billed individually — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html
- Quotas: "150 paths or tags per second"; "1 wildcard invalidation per second"; no quota on files one tag/wildcard invalidation may clear — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html#limits-invalidations . Whether the 150/s is per account or per distribution is not stated. No maximum items per `CreateInvalidation` request is stated in the current guide.
- Timing (paths): "CloudFront forwards the request to all edge locations within a few seconds, and each edge location starts processing the invalidation immediately" — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation_Requests.html#canceling-invalidations . No completion SLA is published.
- Path invalidation invalidates every cookie/header variant of the object, but query-string variants must be listed (or `path*`) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/invalidation-specifying-objects.html . Under Next's `_rsc` query discriminator that means one path per variant, or a wildcard (1/s quota).

### 2.1 Invalidation by cache tag

- Announced 2026-04-29: "Invalidations take effect in under 5 seconds at P95. The end-to-end completion time, which includes reporting the invalidation status back, is under 25 seconds at P95." "Each cache tag is priced as one path." Available everywhere except the China regions — https://aws.amazon.com/about-aws/whats-new/2026/04/cloudfront-invalidation-cache-tag/ ; same figures repeated in https://aws.amazon.com/blogs/networking-and-content-delivery/manage-caches-with-precision-using-amazon-cloudfront-invalidation-by-cache-tag/ (which names only Lambda@Edge origin-response as the "add the header at the edge" option; the origin itself may return the header directly).
- Mechanism: distribution `CacheTagConfig.HeaderName` names an origin response header whose comma-separated values become tags; invalidate with `--paths "#tag"`; opt-in; ≤ 50 tags stored per object (extra ignored); tag ≤ 256 chars, ASCII 33–126, no spaces/commas, **case-insensitive**; no wildcards on tags; "CloudFront invalidates every cached variant of every object that carries the specified tag, regardless of associated cookies, headers, or query string parameters"; path and tag items may mix in one batch and count toward the same limits; changing `HeaderName` orphans previously stored tags — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/invalidation-by-tags.html , https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/invalidation-specifying-tags.html
- CloudFormation exposes `DistributionConfig.CacheTagConfig` (update requires no interruption) — https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/aws-properties-cloudfront-distribution-distributionconfig.html
- Header budget: an origin response including headers is capped at 32,768 bytes — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html#limits-general ; Next's 128 × 256 worst case approaches it, and CloudFront keeps only the first 50 anyway.
- The tag header is forwarded to viewers unless removed by a response headers policy (blog above).

## 3. `s-maxage` / `stale-while-revalidate` in CloudFront

- With `max-age` and `s-maxage` both present CloudFront uses `s-maxage`, bounded by the cache policy's Min/Max TTL; without any directive it uses Default TTL; `no-cache/no-store/private` are honoured only when Min TTL is 0; on expiry CloudFront revalidates with the origin and accepts `304` — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html
- `stale-while-revalidate` and `stale-if-error` are supported: stale is served while a background fetch runs, "up to the value of the `stale-while-revalidate` directive or the value of the CloudFront maximum TTL, whichever is less. After the maximum TTL duration, the stale object won't be available from the edge cache" — same page, "Serve stale (expired) content".
- Viewer `Cache-Control`/`Pragma` cannot force a refetch — same page.
- Consequence for a TTL clamp: setting the ISR behaviour's Max TTL to `B` makes every ISR object refresh at CloudFront within `B` (a hard bound); each POP/regional cache/Origin Shield layer that holds the object then sends one conditional GET per `B`. Origin Shield collapses those to "as few as one request going to your origin" per object per window, at an extra per-request charge — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html

## 4. Versioned cache keys with CloudFront Functions + KeyValueStore

- The cache key defaults to host + path; a cache policy adds headers/query/cookies; "You can also modify the cache key by using a … CloudFront Function on a viewer request" — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html . "Cache key normalization" is a listed CloudFront Functions use case; functions run submillisecond, no network, 10 KB code, viewer request/response only, KVS reads only under runtime 2.0 — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-functions-choosing.html
- KVS quotas: key ≤ 512 B, value ≤ 1 KB, store ≤ 5 MB, ≤ 50 keys or 3 MB per update call, 1 store per function, 10 functions per store — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html#limits-keyvaluestores
- Writes: `UpdateKeys` is all-or-nothing and requires the store's current `ETag` in `If-Match` (409 `ConflictException` otherwise), i.e. concurrent writers serialise — https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_kvs_UpdateKeys.html ; the API is global, SigV4A, needs v2 STS session tokens — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-function-restrictions.html#regional-endpoint-for-key-value-store ; values are stable within one invocation, updated between invocations — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/kvs-with-functions-kvp.html
- Propagation: "changes are propagated to all CloudFront edge locations in a few seconds" — https://aws.amazon.com/blogs/aws/introducing-amazon-cloudfront-keyvaluestore-a-low-latency-datastore-for-cloudfront-functions/ . No number in the developer guide.
- Price: functions `$0.10` per million invocations (2 M free/month), KVS reads `$0.03` per million from functions (2 M free/month), other KVS API calls `$1` per 1,000 requests — https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/
- Fit: a per-path version (`path → n`, function appends `n` as a cache-policy header) serves `revalidatePath` on literal paths, and every viewer request pays a function invocation plus a KVS read. `revalidateTag` needs the set of paths carrying the tag at write time; Ocel's tag store holds tag records only (`platform/aws/functions/entrypoints/src/next/tag-clock.mts:107-136`, `cache-store.mts:109`), and building that map is what open-next's DynamoDB tag table exists for (https://opennext.js.org/aws/inner_workings/caching). A per-build generation key sidesteps the map by dropping the entire edge cache per revalidation. Neither is preferable to §2.1 once tag invalidation is priced per call, not per page.

## 5. Ocel's pipeline today (Cloudflare edge) and the native mapping

- Origin: `revalidateTag`/`revalidatePath` → cache handler `updateTags` → in-memory record + DynamoDB `writeTag` (`platform/aws/functions/entrypoints/src/next/tag-clock.mts:107-136`, `cache-store.mts:1-51,109`); origin re-syncs its clock every 2 s (`tag-clock.mts:25`).
- Substrate: state-table stream → tag publisher Lambda, batch 100, batching window 0 (`platform/aws/provider/bootstrap/publisher.go:22,134-138`); Lambda polls DynamoDB streams "at a base rate of 4 times per second" and invokes as soon as records are available — https://docs.aws.amazon.com/lambda/latest/dg/with-ddb.html . The publisher merges the tag snapshot into S3 and raises it to the edge writer (`platform/aws/functions/tag-publisher/src/publish.mts:16-32`, `writer.mts:9-27`).
- Cloudflare edge: cached entries are checked against a tag snapshot memoised for 1 s and cached for 6–10 s (`platform/edge/cloudflare/workers/entry/src/tag-clock.ts:42-49,132`), so its coherence bound is roughly publisher latency + ≤ 10 s. Tags come from the prerender manifest (`frameworks/next/adapter/src/next-adapter.mts:779-803`) and are also stamped as `cache-tag` on stored objects (`platform/edge/cloudflare/workers/entry/src/cache.ts:313`).
- Native mapping: the same publisher, on the same stream event, issues `CreateInvalidation` with `#<tag>` items (batched; ≤ 150 items/s) instead of raising to a Cloudflare writer. Chain: DynamoDB write (in-request) → stream poll ≤ 250 ms + invoke → API call → "< 5 s P95" at the edge. `revalidatePath` is one item; `revalidateTag` is one item per tag.
- open-next, for comparison, has an opt-in "automatic CDN invalidation" override that issues two path invalidations per on-demand-revalidated route and warns that tag revalidations "could end up triggering thousands of invalidation requests" — https://opennext.js.org/aws/config/overrides/automatic_cdn_invalidation ; its docs otherwise say on-demand revalidation "is still necessary to invalidate the CloudFront cache" by hand — https://opennext.js.org/aws/inner_workings/caching . Both predate tag invalidation.

## 6. Constraints the native design must carry

1. Origin emits the tag header itself (Next only does so in `minimalMode`, §1), from the entry's stored `x-next-cache-tags`, truncated to 50 with soft tags first, ASCII-clean (Next already percent-encodes non-ASCII: `dist/server/lib/implicit-tags.js:52-58`; explicit tags with spaces are rejected by CloudFront's format and their fate — dropped or whole header ignored — is not documented).
2. Case folding: two Next tags differing only in case are one CloudFront tag; over-invalidation, never under.
3. `STALE` responses after `revalidateTag(tag,'max')` carry the full `s-maxage` (§1); the origin must clamp `Cache-Control` on `x-nextjs-cache: STALE` (or delay the invalidation until the revalidator's `REVALIDATED` render), or CloudFront re-caches stale content for the whole window. `updateTag`/`{expire:0}` produce a blocking render and need nothing.
4. `_rsc` must be in the cache key (https://nextjs.org/docs/app/guides/cdn-caching); tag invalidation covers all variants, so no per-variant path enumeration.
5. Every distribution needs `CacheTagConfig` and the publisher needs `cloudfront:CreateInvalidation` on the project's distribution.
6. Bound to print: no SLA exists; the defensible statement is "typically under 10 s" backed by AWS's P95 (< 5 s) plus Ocel's stream hop; the only hard bound available is a Max-TTL clamp (§3) at origin-request cost.
