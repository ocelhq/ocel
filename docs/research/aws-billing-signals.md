# AWS billing signals that catch one anomalous S3 day in a linked account

All figures retrieved 2026-09-06. Prices are US East (N. Virginia) unless stated.

## Headlines

1. Nothing in AWS billing sees the fluke day sooner than ~24h: Cost Explorer "reflects your usage up to the previous day", and every billing-derived signal (Budgets, Cost Anomaly Detection, CUR) sits downstream of it.
2. The only sub-hour signal for an S3 request storm is **S3 CloudWatch request metrics** — 1-minute intervals, ~15 min to activate, opt-in per bucket (or per prefix/tag/access point), billed as CloudWatch custom metrics (~$0.30/metric/mo for the first 10,000).
3. A linked account **can** create its own AWS-services Cost Anomaly Detection monitor (quota: "AWS managed monitor for AWS services per account (management and member) = 1") and its own CUR 2.0 / FOCUS export scoped to its own data. Neither needs the payer.
4. Cost Anomaly Detection's **default** alert threshold is $100 absolute **and** 40% of expected spend — a $50 (or $1.74) fluke day is silently recorded and never mailed. The threshold is configurable; the detection floor is not documented.
5. Anomaly detection runs ~3×/day, needs 10 days of history per service, monitors **net unblended, Usage charge type only**, and takes "up to 24 hours to detect an anomaly after a usage occurs".
6. `GetCostAndUsageWithResources` is useless here: it "requires the Expression `SERVICE = Amazon Elastic Compute Cloud - Compute` in the filter", hourly only for EC2, 14-day window. There is no per-bucket resource ID from the Cost Explorer API.
7. Cost Explorer **hourly granularity is payer-gated** ("Using the management account, you can enable multi-year data and granular data"), takes up to 48h to take effect, covers the past 14 days, and costs $0.00000033/usage-record/day ($0.01 per 1,000 records/month).
8. CloudWatch `AWS/Billing EstimatedCharges` is a dead end for a linked account: "member linked account metrics are captured only if the payer account enables the Receive Billing Alerts preference", and the data is readable only from the payer account, in us-east-1.
9. Cost allocation tags are payer-only to activate — but since March 2024 the payer can **backfill up to twelve months**, so a missed activation is recoverable, not lost forever.
10. Cheapest useful standalone stack: a member-created anomaly monitor with a low custom threshold (free) + `GetCostAndUsage` DAILY polling at $0.01/request (~$1.20/mo at 4×/day) + a member-owned hourly CUR 2.0 export (S3 costs only). Detection floor stays ~24h.

## Cost Explorer API

`GetCostAndUsage` accepts `DAILY | MONTHLY | HOURLY` and is the only signal that needs no prior setup beyond IAM ([API ref](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_GetCostAndUsage.html)). Grouping by `SERVICE` and `USAGE_TYPE` is enough to separate S3 request charges (`Requests-Tier1`) from storage; `RESOURCE_ID` is not a valid `GroupBy` dimension on this operation.

Latency is the binding constraint. Cost Explorer states plainly: "All costs reflect your usage up to the previous day. For example, if today is December 2, the data includes your usage through December 1", with the caveat that "some data might be updated later than 24 hours" ([exploring data](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/ce-exploring-data.html)). So a fluke day that starts at 00:30 UTC is visible no earlier than the next day, and polling more often than a few times a day buys nothing.

Cost: "$0.01 per request. Please note that if your result set is paginated each page counts as a separate request" ([CE pricing](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/pricing/), [FAQ](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/faqs/)). Four polls a day is $1.20/month; per-usage-type grouping keeps responses to one page for a small account.

**Hourly granularity** would tighten the picture within a day, but it is a Cost Management *preference*: "Using the management account, you can enable multi-year data and granular data in Cost Explorer... The hourly data as well as daily resource-level data is available for the past 14 days" and "It can take up to 48 hours for changes to your data settings to reflect in Cost Explorer" ([configuring data](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-configuring-data.html), [services hourly](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-services-hourly.html)). Standing cost is $0.00000033 per usage record per day, "$0.01 per 1,000 usage records monthly"; a usage record is "a line item with a specific resource and usage type" ([hourly granularity cost](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-hourly-granularity.html)). Because the setting is listed among the preferences a member account inherits ([ce-access](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-access.html)), a linked account cannot turn it on for itself. **Unverified:** whether `GetCostAndUsage` with `Granularity: HOURLY` from a member account whose payer has not opted in returns `DataUnavailableException` or empty results — the API reference documents `DataUnavailableException` but does not tie it to this setting.

`GetCostAndUsageWithResources` does not help. It is opt-in ("This is an opt-in only feature. You can enable this feature from the Cost Explorer Settings page"), "Hourly granularity is only available for EC2-Instances", the time period "must be within the last 14 days", and the filter "requires the Expression `SERVICE = Amazon Elastic Compute Cloud - Compute`" ([API ref](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_GetCostAndUsageWithResources.html)). There is no path from this API to per-bucket S3 attribution.

## BCM Data Exports / CUR 2.0

A member account can create its own export, and it gets exactly its own data: "If you're using a member account, your CUR 2.0 table only includes cost and usage data for that member account", and "a member account can only export data for the time that the account has been a member of the organization" ([CUR 2.0 table](https://docs.aws.amazon.com/cur/latest/userguide/table-dictionary-cur2.html)). No payer action is required beyond the S3 bucket the export writes to, which the member owns.

Table configurations carry the levers that matter: `TIME_GRANULARITY` = `HOURLY | DAILY | MONTHLY`, and `INCLUDE_RESOURCES` which "adds the `line_item_resource_id` column to the table schema... a line item for each resource that incurred usage for a given service". For S3, `line_item_resource_id` is the bucket name — which is why the map's platform-cost gap is real: a shared state bucket is one resource ID no matter how many projects wrote to it. The 125-column schema includes a **Resource tags** group and a nested **Tags** column ("Data about user, account, cost category and resource tags"), so tag columns exist but are populated only for tags the payer has activated.

Export types available include CUR 2.0, **FOCUS 1.0 with AWS columns** and FOCUS 1.2, cost optimization recommendations, and carbon emissions ([what is Data Exports](https://docs.aws.amazon.com/cur/latest/userguide/what-is-data-exports.html)). Compression/format choices are Parquet, gzip/CSV, or zip/CSV, with an Athena-optimised preset ([create standard export](https://docs.aws.amazon.com/cur/latest/userguide/dataexports-create-standard.html)).

Cadence is the disappointment. For a Data Export, "the only option available is **Daily — export is refreshed up to one time per day**". Legacy CUR is documented as updating "up to three times a day" and "at least once a day until your charges are finalized", with "up to 24 hours for AWS to deliver the first report" ([what is CUR](https://docs.aws.amazon.com/cur/latest/userguide/what-is-cur.html)). So CUR 2.0 is the *richest* signal and roughly the *slowest*: first data up to 24h after export creation, then daily. It is the right substrate for attribution and effective-rate work, and the wrong one for catching a day in flight.

**Unverified:** typical Parquet file sizes. AWS documents only that a report "can grow to more than a gigabyte" and is split at roughly a million rows; no per-row or per-account size figure is published.

## AWS Cost Anomaly Detection

This is the strongest zero-cost candidate and it works from inside a linked account. The quota table is explicit: "AWS managed monitor for AWS services per account (management and member) = 1", "Total AWS managed monitors per member account = 1", while linked-account, cost-allocation-tag and cost-category monitors are management-account only ([quotas](https://docs.aws.amazon.com/cost-management/latest/userguide/management-limits.html), [getting started](https://docs.aws.amazon.com/cost-management/latest/userguide/getting-started-ad.html)). The AWS-services monitor "automatically evaluates all AWS services used by your account" and is "Available in both management and member accounts" — precisely the standalone case.

Mechanics: "After your billing data is processed, AWS Cost Anomaly Detection runs approximately three times a day... Cost Anomaly Detection uses data from Cost Explorer, which has a delay of up to 24 hours. As a result, it can take up to 24 hours to detect an anomaly after a usage occurs. If you create a new monitor, it can take 24 hours to begin detecting new anomalies. For a new service subscription, 10 days of historical service usage data is needed before anomalies can be detected for that service" ([manage-ad](https://docs.aws.amazon.com/cost-management/latest/userguide/manage-ad.html)). The quota table repeats: time to detect = up to 24 hours, historical data required = 10 days minimum, and the analysis is limited to "Usage charge type and NetUnblendedCost".

Alerting: **Individual alerts** "notify you as soon as an anomaly is detected... These notifications require an Amazon SNS topic" (one SNS topic per subscription, up to 10 email recipients). Daily summaries are generated at 00:00 UTC and can therefore add most of a day. Thresholds are absolute (dollar impact) or percentage, combinable with AND/OR.

The trap for ocel: the default configuration AWS auto-creates for new Cost Explorer users "will generate alerts for all anomalies that will both exceed 40% of what is identified by the CAD ML model as expected spend as well as a minimal USD amount (a fixed amount threshold) of $100" ([CAD FAQs](https://aws.amazon.com/aws-cost-management/aws-cost-anomaly-detection/faqs/)). The dogfood account's Aug 9 was 87× the trailing rate at $1.74 — it clears 40% by a mile and fails $100 outright. `ocel cost init` must create its own subscription with a low absolute threshold; "even if an anomaly is below the alert threshold, the machine learning model continues to detect spend anomalies" and all anomalies remain listed under Detected anomalies, so a poller of `GetAnomalies` can undercut the alert threshold entirely. **Unverified:** whether AWS applies an undocumented internal floor below which no anomaly object is created at all.

Cost: the service is free; the SNS topic is effectively free at this volume.

## AWS Budgets

"By default, owners of member accounts can create their own budgets but can't create or edit budgets for other users", and "A budget is only visible to users with access to the account that created the budget" ([managing costs](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)). So a linked account can self-serve.

Cadence: "AWS Budgets information is updated up to three times a day. Updates typically occur 8–12 hours after the previous update", with the standing caveat that "There can be a delay between when you incur a charge and when you receive a notification". That is better than daily but still downstream of the same 24h billing pipeline.

Cost: budget monitoring and notifications are free; "Your first two action-enabled budgets are free... per month", then $0.10 per action-enabled budget per day; budget reports are $0.01 per delivered report ([Budgets pricing](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/)). Quotas: 2 free budgets with actions per account, 10 actions per budget, 100 budget actions per account, 20,000 budgets per management account.

For the fluke day specifically, an absolute monthly cost budget is the wrong shape — the map already observed that $1.74 on a month tracking to $3.25 fires nothing. A *daily* budget, or a usage budget on S3 `Requests-Tier1`, is the shape that fires; both are creatable by the member account.

## CloudWatch `AWS/Billing EstimatedCharges`

Rule this out for the standalone linked-account case. The metric is calculated and "sent several times daily to CloudWatch" and stored in us-east-1, but: "You must be signed in using account root user credentials or as an IAM user that has been given permission to view billing information"; "For consolidated billing accounts, billing data for each linked account can be found by logging in as the paying account"; and decisively, "In a consolidated billing account, member linked account metrics are captured only if the payer account enables the **Receive Billing Alerts** preference" ([billing alarms](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/monitor_estimated_charges_with_cloudwatch.html)). The metric also carries only total and per-service estimates, never per-bucket. Cost is one standard alarm at $0.10/month.

## S3 request metrics, Storage Lens, CloudTrail

**S3 request metrics** are the only genuinely fast signal and the only one that attributes requests below the bucket. "Storage metrics are reported once per day and are provided to all customers at no additional cost. Request metrics are available at one-minute intervals after some latency for processing. Request metrics are billed at the standard CloudWatch rate. You must opt in to request metrics"; "After about 15 minutes, CloudWatch begins tracking these request metrics" ([configure request metrics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/configure-request-metrics-bucket.html)). A metrics configuration can filter "by prefix, object tag, or access point" and surfaces as the `FilterId` dimension ([metrics and dimensions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/metrics-dimensions.html)) — this is the mechanism that could attribute Pulumi state churn per project prefix inside one shared bucket. Caveat from AWS: delivery is "best-effort... not meant to be a complete accounting of all requests", so these are a detector, never a ledger. Cost is CloudWatch custom metrics: $0.30/metric/month for the first 10,000, $0.10 for 10,001–250,000 ([CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/)). A single `EntireBucket` filter publishes on the order of a dozen metrics — a few dollars a month per bucket, dominating the $3.25 bill it is watching.

**Storage Lens** free tier gives daily summary/cost-optimization/data-protection metrics with 14-day query retention; **activity metrics (all requests, GET/PUT counts, bytes) and prefix-level aggregation are advanced tier only**, with 15-month retention and optional CloudWatch publishing ([Storage Lens basics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage_lens_basics_metrics_recommendations.html)). Advanced tier is $0.20 per million objects per month for the first 25B objects (AWS Price List API, `USE1-StorageLens-ObjCount`, retrieved 2026-09-06). At 189,788 objects on the preview state bucket that is ~$0.04/month — cheap — but all metrics "are collected daily", so it detects the day after, not during. Its outlier call-outs use a z-score against the trailing 30 days (|z| > 2), which is conceptually the map's velocity guard, already built and daily.

**CloudTrail data events** as a request-volume proxy: "$0.10 per 100,000 data events delivered" to S3, plus S3 storage ([CloudTrail pricing](https://aws.amazon.com/cloudtrail/pricing/)). The 348k-request Aug 9 would have cost ~$0.35 to log — 20% of the anomaly itself — and every ordinary day pays too. Rejected on cost/benefit except as a targeted, time-boxed investigation tool.

For reference, the request rates that make this a request-cost problem at all (AWS Price List API, `AmazonS3` / `us-east-1`, retrieved 2026-09-06): S3 Standard `Requests-Tier1` $0.000005/request ($0.005 per 1,000), `Requests-Tier2` $0.0000004; **One Zone-IA** `Requests-ZIA-Tier1` $0.00001 ($0.01 per 1,000) — 2× Standard — `Requests-ZIA-Tier2` $0.000001, plus `Retrieval-ZIA` $0.01/GB.

## What the payer must grant, and detecting that it hasn't

Three payer-side gates, in descending order of consequence:

1. **Cost Explorer enablement and linked-account access.** "Enabling Cost Explorer at the management account level enables Cost Explorer for all of your organization accounts... you can't grant or deny access individually", and the payer can clear **Linked account access** under Member account permissions, which revokes a member's view of its own data ([ce-access](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-access.html)). Detection from inside: call `ce:GetCostAndUsage` for yesterday; `AccessDeniedException` is the signal. Note that this is *not* the console's **Activate IAM Access** switch — that setting explicitly "doesn't control access to... The Billing and Cost Management SDK APIs (AWS Cost Explorer, AWS Budgets, and AWS Cost and Usage Reports APIs)" ([control access](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/control-access-billing.html)), so an API-only tool never needs it.
2. **Cost allocation tag activation.** "Only the management account in an organization and single accounts that aren't members of an organization have access to the cost allocation tags manager" ([cost-alloc-tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)). Activation takes up to 24h to appear and up to another 24h to activate ([activating tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/activating-tags.html)). Detection from inside: `ce:ListCostAllocationTags` filtered to `Status: Active` and the `ocel:*` keys — an absent key means unactivated. **Partly unverified:** the API reference documents no member-account restriction, so whether a member sees the payer's activation state or an empty list needs an account test.
3. **Hourly/resource-level granularity.** Payer-only, 48h to apply, and locked for 48h after each change.

The map's sketch records tag activation as "not retroactive, every day off is unattributable forever". That is now wrong: "Management account users can request a backfill of cost allocation tags for up to twelve months... the current activation status of the tags are backfilled for the duration of your choice", subject to "The resource tag must be historically assigned to the AWS Resource", one request per 24h, and propagation on the normal daily refresh ([backfill](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-allocation-backfill.html)). Late activation costs a request, not the history — provided the tags were on the resources at the time.

## Open questions

- Does `GetCostAndUsage` with `Granularity: HOURLY` from a member account fail with `DataUnavailableException` when the payer has not opted in, or return zeros? Needs an account test; it determines whether `ocel cost doctor` can probe the setting cheaply.
- Does `ListCostAllocationTags` from a member account return the payer's activation state, an empty list, or an error? The API reference documents no restriction, but the console manager is payer-only.
- Is there an undocumented dollar floor below which Cost Anomaly Detection creates no anomaly object at all? If so, `GetAnomalies` polling cannot undercut the alert threshold arbitrarily, and the $1.74-class day may be invisible to CAD regardless of configuration.
- What Parquet size does a single-account hourly CUR 2.0 export with resource IDs actually produce per month? AWS publishes no per-row figure; this sizes the in-account collector.
- Does an S3 metrics configuration filtered by prefix publish a full metric set per `FilterId` (and therefore multiply the CloudWatch bill by the number of prefixes watched)? Pricing implies yes; not stated in the S3 docs.
- Are `Requests-Tier1` usage budgets expressible per bucket, or only per service and usage type? If only the latter, a usage budget cannot separate platform buckets from workload buckets.
